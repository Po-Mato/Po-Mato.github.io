1e:T6d96,<h2 id="section-서론-에이전트가-멈추는-순간" tabindex="-1">서론: 에이전트가 멈추는 순간<a href="#section-%EC%84%9C%EB%A1%A0-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%EA%B0%80-%EB%A9%88%EC%B6%94%EB%8A%94-%EC%88%9C%EA%B0%84" class="heading-anchor" aria-label="서론: 에이전트가 멈추는 순간 항목 링크">#</a></h2>
<p>4월 13일의 글에서 Agent SLO와 Failure Recovery 패턴을 discussed했다. 그 글의 결론 중 하나는 "에이전트의 실패는 통상적인 HTTP 타임아웃과 다르다"는 것이었다. 사용자가 "삼성전자 재무제표 분석해줘"라고 요청하면, 에이전트는 수십 개의 내부 단계를 거친다 — 웹 검색, 데이터 파싱, 계산, 문서 생성. 그 어떤 단계에서든 실패할 수 있고, 실패 시 사용자는 그냥 "실패했습니다"만 받는다.</p>
<p>2026년 현재, 이 문제는 기업 AI 도입의 가장 큰 마찰점 중 하나다. Durable execution — 작업의 중간 상태를 저장하고, 실패 시 마지막 성공 지점에서 재개하는 능력 — 이 그 해법이다.</p>
<hr>
<h2 id="section-1-durable-execution이란-무엇인가" tabindex="-1">1. Durable Execution이란 무엇인가<a href="#section-1-durable-execution%EC%9D%B4%EB%9E%80-%EB%AC%B4%EC%97%87%EC%9D%B8%EA%B0%80" class="heading-anchor" aria-label="1. Durable Execution이란 무엇인가 항목 링크">#</a></h2>
<h3 id="section-전통적-실행-모델의-한계" tabindex="-1">전통적 실행 모델의 한계<a href="#section-%EC%A0%84%ED%86%B5%EC%A0%81-%EC%8B%A4%ED%96%89-%EB%AA%A8%EB%8D%B8%EC%9D%98-%ED%95%9C%EA%B3%84" class="heading-anchor" aria-label="전통적 실행 모델의 한계 항목 링크">#</a></h3>
<p>일반적인 API 호출 모델에서 함수는 실행되거나 실패한다. 실패하면 예외를 던지고 호출자가 처리한다. 재시도가 필요하면 명시적으로 구현해야 한다.</p>
<pre><code>[API Request] → [Function Executes] → [Success OR Exception]
                 ↑ 이 사이에 100단계가 있어도
                 실패 시 전체 롤백
</code></pre>
<h3 id="section-durable-execution의-모델" tabindex="-1">Durable Execution의 모델<a href="#section-durable-execution%EC%9D%98-%EB%AA%A8%EB%8D%B8" class="heading-anchor" aria-label="Durable Execution의 모델 항목 링크">#</a></h3>
<p>Durable execution은 함수의 실행 상태를 인프라 레벨에서 추적한다. 각 단계(signal)가 완료될 때마다 상태를 persistence layer에 기록한다. 프로세스가 충돌해도, 마지막 완료된 단계에서 재개한다.</p>
<pre><code>[Step 1] → [Step 2] → [Step 3] → [CRASH] → [Resume from Step 3]
              ↓          ↓          ↓
          [Saved]    [Saved]     [Saved]
</code></pre>
<p>이 모델은 단순 재시도와 다르다. 단순 재시드는 "실패하면 처음부터"이지만, durable execution은 "실패하면 이미 완료된 작업을 반복하지 않음"을 보장한다.</p>

<h2 id="section-2-ai-agent에서-durable-execution이-중요한-이유" tabindex="-1">2. AI Agent에서 Durable Execution이 중요한 이유<a href="#section-2-ai-agent%EC%97%90%EC%84%9C-durable-execution%EC%9D%B4-%EC%A4%91%EC%9A%94%ED%95%9C-%EC%9D%B4%EC%9C%A0" class="heading-anchor" aria-label="2. AI Agent에서 Durable Execution이 중요한 이유 항목 링크">#</a></h2>
<h3 id="section-에이전트의-본질-장시간-비결정적-태스크" tabindex="-1">에이전트의 본질: 장시간, 비결정적 태스크<a href="#section-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%EC%9D%98-%EB%B3%B8%EC%A7%88-%EC%9E%A5%EC%8B%9C%EA%B0%84-%EB%B9%84%EA%B2%B0%EC%A0%95%EC%A0%81-%ED%83%9C%EC%8A%A4%ED%81%AC" class="heading-anchor" aria-label="에이전트의 본질: 장시간, 비결정적 태스크 항목 링크">#</a></h3>
<p>LLM 기반 에이전트는 다음과 같은 고유한 특성을 가진다:</p>
<ol>
<li><strong>비결정적 실행</strong>: 같은 입력이라도 모델이 다르게 응답할 수 있음</li>
<li><strong>장시간 실행</strong>: 복잡한 태스크는 수십 초~수 분이 소요됨</li>
<li><strong>멀티스텝 의존성</strong>: 앞 단계의 출력이 뒤 단계의 입력으로 사용됨</li>
<li><strong>외부 의존성</strong>: 웹 검색, API 호출, 파일 시스템 등 네트워크 IO에 의존</li>
</ol>
<h3 id="section-실패-시나리오-분석" tabindex="-1">실패 시나리오 분석<a href="#section-%EC%8B%A4%ED%8C%A8-%EC%8B%9C%EB%82%98%EB%A6%AC%EC%98%A4-%EB%B6%84%EC%84%9D" class="heading-anchor" aria-label="실패 시나리오 분석 항목 링크">#</a></h3>
<pre><code>[사용자 요청]
    ↓
[Plan 생성] → 실패 시 → 처음부터 Plan 재생성 (API 비용 낭비)
    ↓
[웹 검색 x5] → 3개만 성공, 2개 실패 → 성공한 것만 사용? 처음부터 재시도?
    ↓
[데이터 파싱] → 파싱 실패 → 어떻게 recovery?
    ↓
[보고서 생성] → 중간에 연결 끊김 → 얼마나 많이 날아갔는가?
</code></pre>
<p>传统的 재시도 구조에서는 이 모든 단계가 처음부터 다시 시작된다. Plan 생성부터 다시 하고, 검색을 다시 하고. 비용과 시간이 낭비된다.</p>
<h3 id="section-durable-execution이-해결하는-것" tabindex="-1">Durable Execution이 해결하는 것<a href="#section-durable-execution%EC%9D%B4-%ED%95%B4%EA%B2%B0%ED%95%98%EB%8A%94-%EA%B2%83" class="heading-anchor" aria-label="Durable Execution이 해결하는 것 항목 링크">#</a></h3>
<ol>
<li><strong>멀티스텝 롱테스트의 원자성</strong>: 전체 태스크를 하나의 durable한 작업으로 감싸서, 실패 지점부터 재개</li>
<li><strong>검증된 스텝 재실행 방지</strong>: 완료된 스텝은 두 번 실행되지 않음 (idempotency 보장)</li>
<li><strong>사용자 대기 시간 관리</strong>: 긴 작업의 진행 상황을 사용자에게 투명하게 제공</li>
<li><strong>비용 최적화</strong>: 실패 시 불필요한 LLM API 호출 제거</li>
</ol>

<h2 id="section-3-실전-구현-langgraph-checkpointing" tabindex="-1">3. 실전 구현: LangGraph Checkpointing<a href="#section-3-%EC%8B%A4%EC%A0%84-%EA%B5%AC%ED%98%84-langgraph-checkpointing" class="heading-anchor" aria-label="3. 실전 구현: LangGraph Checkpointing 항목 링크">#</a></h2>
<p>LangGraph는 내장된 checkpointing 메커니즘을 제공한다. 상태(state)를 persistence layer에 저장하고, 실패 시 마지막 상태에서 그래프 실행을 재개한다.</p>
<h3 id="section-기본-예제-검색-분석-에이전트" tabindex="-1">기본 예제: 검색 + 분석 에이전트<a href="#section-%EA%B8%B0%EB%B3%B8-%EC%98%88%EC%A0%9C-%EA%B2%80%EC%83%89-%EB%B6%84%EC%84%9D-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8" class="heading-anchor" aria-label="기본 예제: 검색 + 분석 에이전트 항목 링크">#</a></h3>
<pre><code class="language-typescript">import { StateGraph, MemorySaver, Annotation } from "@langchain/langgraph";
import { z } from "zod";

// 상태 스키마 정의
const AgentState = Annotation.Root({
  query: Annotation&#x3C;string>,           // 사용자 질문
  searchResults: Annotation&#x3C;any[]>,     // 검색 결과
  analysis: Annotation&#x3C;string>,        // 분석 결과
  error: Annotation&#x3C;string | null>,     // 에러 상태
  step: Annotation&#x3C;number>,             // 현재 단계 추적
});

// 검색 스텝
async function searchStep(state: typeof AgentState.State) {
  console.log(`[Step ${state.step}] 검색 실행: ${state.query}`);
  
  // 외부 웹 검색 시뮬레이션 (실제로는 Tavily, Serper 등 사용)
  const results = await performWebSearch(state.query);
  
  if (results.length === 0) {
    // 실패 시 상태 저장 후 예외 throw (recovery 포인트)
    throw new Error("검색 결과 없음 — 재시도 필요");
  }
  
  return {
    searchResults: results,
    step: state.step + 1,
    error: null,
  };
}

// 분석 스텝
async function analysisStep(state: typeof AgentState.State) {
  console.log(`[Step ${state.step}] 분석 실행 — ${state.searchResults.length}개 결과`);
  
  const analysis = await performAnalysis(state.searchResults, state.query);
  
  return {
    analysis,
    step: state.step + 1,
  };
}

// 에러 핸들링 스텝
function errorHandler(state: typeof AgentState.State, error: Error) {
  return {
    error: error.message,
    step: state.step,
  };
}

// 그래프 정의
const workflow = new StateGraph(AgentState)
  .addNode("search", searchStep)
  .addNode("analysis", analysisStep)
  .addNode("errorHandler", errorHandler)
  .addEdge("__start__", "search")
  .addConditionalEdges(
    "search",
    (state) => state.error ? "errorHandler" : "analysis"
  )
  .addEdge("analysis", "__end__")
  .addEdge("errorHandler", "__end__")
  .compile();

// Checkpointer 설정 (이것이 핵심)
const checkpointer = new MemorySaver();
const app = workflow.compile({ checkpointer });

// 실패 시나리오: 태스크 실행 중 중단
async function runWithDurability(userQuery: string, threadId: string) {
  try {
    // 첫 실행: 검색까지만 완료 후 '중단'되었다고 가정
    const config = { configurable: { thread_id: threadId } };
    
    // 상태 업데이트만 수행 (중간 저장)
    await app.updateState(config, {
      query: userQuery,
      step: 1,
      searchResults: [{ title: "삼성전자 2025 연간보고서", url: "..." }],
    });
    
    console.log("✅ 상태 저장 완료 — 다음 실행에서从这里 재개");
    
  } catch (error) {
    console.error("에이전트 실행 실패:", error);
  }
}

// 재개 실행: 저장된 상태에서 pick up
async function resumeExecution(threadId: string) {
  const config = { configurable: { thread_id: threadId } };
  
  // checkpointer가 자동으로 마지막 상태를 복원
  const existingState = await app.getState(config);
  console.log(`재개: Step ${existingState.values.step}부터 계속`);
  
  const result = await app.invoke(null, config);
  console.log("최종 분석 결과:", result.analysis);
}
</code></pre>
<h3 id="section-checkpointing-아키텍처-내부" tabindex="-1">Checkpointing 아키텍처 내부<a href="#section-checkpointing-%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98-%EB%82%B4%EB%B6%80" class="heading-anchor" aria-label="Checkpointing 아키텍처 내부 항목 링크">#</a></h3>
<p>LangGraph의 checkpointing은 3단계로 동작한다:</p>
<pre><code>[Checkpointer Interface]
        ↓
┌──────────────────────────────────────┐
│  1. dump(state) → serialized blob   │
│     - 전체 상태 그래프를 직렬화        │
│     - 스레드 ID별로 구분               │
│                                      │
│  2. load(thread_id) → state         │
│     - 마지막 checkpoint 복원           │
│     - 간으한 경우 diff 기반 증분 저장  │
│                                      │
│  3. get_versions                     │
│     - 히스토리 조회 지원               │
└──────────────────────────────────────┘
        ↓
[Persistence Layer]
  - MemorySaver (개발/테스트)
  - SqliteSaver (로컬 프로덕션)
  - PostgresSaver (분산 프로덕션)
  - Custom (Redis, etc.)
</code></pre>

<h2 id="section-4-temporal를-활용한-엔터프라이즈-级-durable-agent" tabindex="-1">4. Temporal를 활용한 엔터프라이즈 级 Durable Agent<a href="#section-4-temporal%EB%A5%BC-%ED%99%9C%EC%9A%A9%ED%95%9C-%EC%97%94%ED%84%B0%ED%94%84%EB%9D%BC%EC%9D%B4%EC%A6%88-%E7%BA%A7-durable-agent" class="heading-anchor" aria-label="4. Temporal를 활용한 엔터프라이즈 级 Durable Agent 항목 링크">#</a></h2>
<p>LangGraph checkpointing이 경량 통합에 적합하다면, Temporal은 복잡한 엔터프라이즈 시나리오에 적합하다. Temporal은 워크플로우를 코드로 정의하고, 인프라에서完全的 내구성을 보장한다.</p>
<h3 id="section-temporal-워크플로우로-에이전트-태스크-모델링" tabindex="-1">Temporal 워크플로우로 에이전트 태스크 모델링<a href="#section-temporal-%EC%9B%8C%ED%81%AC%ED%94%8C%EB%A1%9C%EC%9A%B0%EB%A1%9C-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8-%ED%83%9C%EC%8A%A4%ED%81%AC-%EB%AA%A8%EB%8D%B8%EB%A7%81" class="heading-anchor" aria-label="Temporal 워크플로우로 에이전트 태스크 모델링 항목 링크">#</a></h3>
<pre><code class="language-typescript">import { ProxyAwareness } from "@temporalio/client";
import { workflow, proxyActivities } from "@temporalio/workflow";

// 외부 Activity 정의
const activities = {
  searchWeb: async (query: string) => { /* ... */ },
  analyzeData: async (data: any[]) => { /* ... */ },
  generateReport: async (analysis: string) => { /* ... */ },
  sendNotification: async (userId: string, msg: string) => { /* ... */ },
};

// 워크플로우: 실패해도 자동으로 재개
export async function stockAnalysisWorkflow(userQuery: string, userId: string) {
  // Activity Proxy — Temporal 런타임이 failure → retry를 자동 처리
  const { searchWeb, analyzeData, generateReport, sendNotification } =
    proxyActivities({ activities, startToCloseTimeout: "10m" });

  let step = 0;
  
  try {
    // Step 1: 웹 검색 (재시도 정책: 3번, 지수 백오프)
    console.log(`[Workflow Step ${++step}] 웹 검색 시작`);
    const searchResults = await searchWeb(userQuery);
    
    // Step 2: 데이터 분석
    console.log(`[Workflow Step ${++step}] 데이터 분석 시작`);
    const analysis = await analyzeData(searchResults);
    
    // Step 3: 보고서 생성
    console.log(`[Workflow Step ${++step}] 보고서 생성 시작`);
    const report = await generateReport(analysis);
    
    // Step 4: 완료 알림 (비동기 — 실패해도 태스크는 완료로 표시)
    await sendNotification(userId, `분석 완료: ${report.summary}`);
    
    return { success: true, report };
    
  } catch (err) {
    // 실패 시 계속해서 재시도 (Temporal의 내장 재시도 정책)
    console.error(`[Workflow] Step ${step} 실패 — Temporal이 재시도 스케줄링`);
    throw err;
  }
}

<h3 id="section-temporal의-재시도-메커니즘" tabindex="-1">Temporal의 재시도 메커니즘<a href="#section-temporal%EC%9D%98-%EC%9E%AC%EC%8B%9C%EB%8F%84-%EB%A9%94%EC%BB%A4%EB%8B%88%EC%A6%98" class="heading-anchor" aria-label="Temporal의 재시도 메커니즘 항목 링크">#</a></h3>
<p>Temporal의 가장 강력한 특성 중 하나는 <strong>실패 메커니즘이 워크플로우 코드와 분리</strong>되어 있다는 점이다:</p>
<pre><code>[Activity 실행]
    ↓
[성공?] → Yes → [다음 Activity]
    ↓ No
[재시도 정책 확인]
    - Max attempts exceeded? → Workflow Failure (珠三角)
    - Retryable error? → Wait (backoff) → 재실행
    - Non-retryable error? → Immediate failure
</code></pre>
<pre><code class="language-typescript">// 재시도 정책 커스터마이징
const activityConfig = {
  searchWeb: {
    startToCloseTimeout: "5m",
    retry: {
      maximumAttempts: 5,
      initialInterval: "10s",
      backoffCoefficient: 2.0,        // 10s → 20s → 40s → ...
      maximumInterval: "10m",
      nonRetryableErrorTypes: ["ValidationError", "AuthError"],
    },
  },
};
</code></pre>
<h3 id="section-에이전트-워크플로우와-temporal의-조합" tabindex="-1">에이전트 워크플로우와 Temporal의 조합<a href="#section-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8-%EC%9B%8C%ED%81%AC%ED%94%8C%EB%A1%9C%EC%9A%B0%EC%99%80-temporal%EC%9D%98-%EC%A1%B0%ED%95%A9" class="heading-anchor" aria-label="에이전트 워크플로우와 Temporal의 조합 항목 링크">#</a></h3>
<p>실전에서는 에이전트의 판단 로직과 Temporal의 내구성을 결합한다:</p>
<pre><code class="language-typescript">export async function agenticWorkflow(input: AgentInput) {
  const { searchWeb, callLLM, saveToDB } = proxyActivities({ activities });
  
  // LLM이 다음 액션을 결정 (LLM = 에이전트의 "두뇌")
  let state: AgentState = { history: [], currentTask: input.task };
  
  while (state.remainingTasks.length > 0 &#x26;&#x26; state.iterations &#x3C; 20) {
    // LLM이 다음 액션 결정
    const decision = await callLLM({
      prompt: buildPrompt(state),
      model: "claude-sonnet-4",
    });
    
    const action = parseAction(decision);
    
    // 액션 실행 (Temporal이 내구성 보장)
    const result = await executeAction(action, {
      searchWeb,
      // 기타 액션...
    });
    
    // 상태 업데이트
    state.history.push({ action, result });
    state.remainingTasks = updateTaskList(state.remainingTasks, action);
    
    // 중간 저장 (Temporal이 이 지점을 checkpoint로 자동 관리)
    await saveToDB({ threadId: input.threadId, state });
  }
  
  return summarize(state);
}

<h2 id="section-5-에러-분류와-recovery-전략" tabindex="-1">5. 에러 분류와 Recovery 전략<a href="#section-5-%EC%97%90%EB%9F%AC-%EB%B6%84%EB%A5%98%EC%99%80-recovery-%EC%A0%84%EB%9E%B5" class="heading-anchor" aria-label="5. 에러 분류와 Recovery 전략 항목 링크">#</a></h2>
<p>Durable execution을 구현할 때, 모든 에러를 동일하게 처리하면 안 된다. 에러를 분류하고 각각에 다른 recovery 전략을 적용해야 한다.</p>
<h3 id="section-ai-agent-에러-분류-체계" tabindex="-1">AI Agent 에러 분류 체계<a href="#section-ai-agent-%EC%97%90%EB%9F%AC-%EB%B6%84%EB%A5%98-%EC%B2%B4%EA%B3%84" class="heading-anchor" aria-label="AI Agent 에러 분류 체계 항목 링크">#</a></h3>
<pre><code>[에러 타입]
├── LLM API Error
│   ├── Rate Limit (429) → 지수 백오프 후 재시도 ✓
│   ├── Auth Error (401) → 롤백, 관리자 알림 ✗
│   └── Server Error (500/503) → 재시도 (비동기) ✓
│
├── External Tool Error  
│   ├── Search API 실패 → 대체 검색 엔진 사용 ✓
│   ├── 브라우저 타임아웃 → 스크린샷으로 fallback ✓
│   └── Rate Limit → 큐에 넣고 나중에 재시도 ✓
│
├── Business Logic Error
│   ├── 데이터 불일치 → 부분 결과로 계속 (graceful degradation) ✓
│   └── 검증 실패 → 사용자에게 명확한 피드백 제공 ✗
│
└── Infrastructure Error
    ├── Temporal Worker 다운 → 다른 Worker가 픽업 ✓
    ├── DB 연결 실패 → 재시도 + alerting ✓
    └── 네트워크 파티션 → Circuit Breaker 패턴 ✗
</code></pre>
<h3 id="section-circuit-breaker-구현" tabindex="-1">Circuit Breaker 구현<a href="#section-circuit-breaker-%EA%B5%AC%ED%98%84" class="heading-anchor" aria-label="Circuit Breaker 구현 항목 링크">#</a></h3>
<pre><code class="language-typescript">class CircuitBreaker {
  private failures = 0;
  private lastFailure = 0;
  private state: "closed" | "open" | "half-open" = "closed";
  
  constructor(
    private threshold: number = 5,
    private timeout: number = 60000,  // 1분
  ) {}
  
  async execute&#x3C;T>(fn: () => Promise&#x3C;T>): Promise&#x3C;T> {
    if (this.state === "open") {
      if (Date.now() - this.lastFailure > this.timeout) {
        this.state = "half-open";  // 복구 시도
      } else {
        throw new Error("Circuit breaker open — fast fail");
      }
    }
    
    try {
      const result = await fn();
      this.onSuccess();
      return result;
    } catch (error) {
      this.onFailure();
      throw error;
    }
  }
  
  private onSuccess() {
    this.failures = 0;
    this.state = "closed";
  }
  
  private onFailure() {
    this.failures++;
    this.lastFailure = Date.now();
    if (this.failures >= this.threshold) {
      this.state = "open";
    }
  }
}

// 사용 예
const breaker = new CircuitBreaker({ threshold: 3, timeout: 30000 });

// searchWeb Activity를 circuit breaker로 감싸기
const resilientSearch = (query: string) => 
  breaker.execute(() => searchWeb(query));
</code></pre>

<pre><code class="language-typescript">export async function humanInTheLoopWorkflow(task: Task) {
  const { executeStep, requestApproval, saveResult } = proxyActivities({ activities });
  
  const state = await loadState(task.threadId);
  
  for (const step of state.pendingSteps) {
    if (step.requiresApproval) {
      // 사람에게 승인 요청 — 여기서 워크플로우가 PAUSE 상태로 유지됨
      const approval = await requestApproval({

        description: step.description,

      }
    }

    await saveResult({ stepId: step.id, result, timestamp: Date.now() });
  }
  
  return { status: "completed" };
}

<h2 id="section-결론-durable-execution은-선택이-아니라-필수" tabindex="-1">결론: Durable Execution은 선택이 아니라 필수<a href="#section-%EA%B2%B0%EB%A1%A0-durable-execution%EC%9D%80-%EC%84%A0%ED%83%9D%EC%9D%B4-%EC%95%84%EB%8B%88%EB%9D%BC-%ED%95%84%EC%88%98" class="heading-anchor" aria-label="결론: Durable Execution은 선택이 아니라 필수 항목 링크">#</a></h2>
<p>2026년 현재, AI Agent를 프로덕션에서 운영하는 것은 단순히 LLM API를 호출하는 것이 아니다. 복잡한 멀티스텝 태스크를 내구성 있게 실행하는 것이 핵심 역량이다.</p>
<p><strong>Durable execution이 해결하는 3가지 핵심 문제:</strong></p>
<ol>
<li><strong>비용 낭비 방지</strong>: 완료된 스텝의 재실행 제거</li>
<li><strong>사용자 경험</strong>: 실패해도-progress가 사라지지 않음</li>
<li><strong>운영 신뢰도</strong>: 모니터링과 재시도로 자동 복구</li>
</ol>
<p>LangGraph의 checkpointing으로 시작하고, 복잡한 엔터프라이즈 시나리오에는 Temporal을 도입하는 것이 현실적인 전략이다. 둘 다 persistence layer를 공유하기 때문에 간단한 prototype에서 production으로 scale-up이 자연스럽다.</p>
<p>핵심은 <strong>실패를 예상하고 설계</strong>하는 것이다. 에이전트가 반드시 실패한다는 것이 아니라, "실패할 경우 어떻게 되는가"를 처음부터 설계하는 것이 Durable Execution의 철학이다.</p>
