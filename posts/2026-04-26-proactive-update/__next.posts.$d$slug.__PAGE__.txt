<ul>
<li><strong>"Embeddings万能時代"의 종말</strong>: 2026년, Semantic Search 단독이 agent memory에 부적합하다는 인식이 확산되고 있다</li>

<li><strong>Google ADK Always On Memory Agent</strong>: Gemini 3.1 Flash-Lite 기반의 external memory layer 패턴</li>
<li><strong>Engram</strong>: Go binary + SQLite FTS5 + MCP server로 Agent-agnostic한 메모리 시스템</li>
<li><strong>자가 검토 결론</strong>: "Simple is correct" — 복잡한 벡터 스토어보다 SQLite FTS5 BM25가 agent memory의 근본 문제에 더 잘 부합한다</li>
</ul>

<h2 id="section-1-서론-왜-ai-agent에게-기억-이-문제인가" tabindex="-1">1. 서론: 왜 AI Agent에게 '기억'이 문제인가<a href="#section-1-%EC%84%9C%EB%A1%A0-%EC%99%9C-ai-agent%EC%97%90%EA%B2%8C-%EA%B8%B0%EC%96%B5-%EC%9D%B4-%EB%AC%B8%EC%A0%9C%EC%9D%B8%EA%B0%80" class="heading-anchor" aria-label="1. 서론: 왜 AI Agent에게 &#x27;기억&#x27;이 문제인가 항목 링크">#</a></h2>
<p>2025년 말을 기점으로 AI Agent가 Production에 본격 도입되면서, 하나의 근본적 한계가 다시 부각되고 있다.</p>
<blockquote>
<p><strong>"LLM은 stateless다. 그러나 Agent는 stateful해야 한다."</strong></p>
</blockquote>
<p>Agent가 하는 일은 단순히 질의에 답하는 것이 아니다:</p>
<ul>
<li>사용자의 선호도를 기억하고个性化해야 한다</li>
<li>이전 작업 결과를 참조하여 연속적 태스크를 수행해야 한다</li>
<li>프로젝트 맥락을 축적하여 시간이 지날수록 더 똑똑해져야 한다</li>
</ul>
<p>기존의 접근은 벡터 데이터베이스에 모든 것을 때려넣는 것이었다. 이 패턴의 문제점은 명확하다:</p>

<tr>
<th>문제</th>
<th>설명</th>

<tr>

</tr>

<p>2026년, 이 문제를 근본적으로 재설계하는 세 가지 아키텍처가 Production에서 검증되고 있다.</p>

<h2 id="section-2-cloudflare-agent-memory-durable-objects-sqlite-vectorize" tabindex="-1">2. <p>Cloudflare는 2026년 4월, Workers 플랫폼 위에 <strong>Agent Memory</strong>를 정식 공개했다. 구조는 놀라울 정도로 단순하다:</p>

<h3 id="section-2-2-핵심-설계-결정-agent별隔离" tabindex="-1">2-2 핵심 설계 결정: Agent별隔离<a href="#section-2-2-%ED%95%B5%EC%8B%AC-%EC%84%A4%EA%B3%84-%EA%B2%B0%EC%A0%95-agent%EB%B3%84%E9%9A%94%E7%A6%BB" class="heading-anchor" aria-label="2-2 핵심 설계 결정: Agent별隔离 항목 링크">#</a></h3>
<p>가장 중요한 설계 결정은 각 Agent에 대한 <strong>Durable Object instance가 1:1로 할당</strong>된다는 것이다.</p>
<pre><code class="language-typescript">// Cloudflare Agent Memory 접근 패턴
// 각 agent는 자신만의 Durable Object instance와 통신
class AgentMemory extends DurableObject {
  async addMemory(content: string, metadata: MemoryMeta) {
    // SQLite: 정확한 사실 저장 (ACID 보장)
    await this.storage.sql.exec(
      `INSERT INTO episodic_memory (content, timestamp, tags)
       VALUES (?, ?, ?)`,
      [content, Date.now(), JSON.stringify(metadata)]
    );

    // Vectorize: 의미적 검색용
    const embedding = await this.env.ai.run('@cf/baai/bge-base-en-v1.5', {
      text: [content]
    });
    await this.env.vectorize.insert(embedding[0], {
      id: crypto.randomUUID(),
      content
    });
  }
}
</code></pre>
<p><strong>왜 이 설계가 중요한가</strong>:</p>
<ul>
<li><strong>ACID 보장</strong>: SQLite의 트랜잭션이 메모리 읽기/쓰기의 일관성을 보장한다. 벡터 DB는 eventual consistency 모델이 기본이다.</li>
<li><strong>Isolation =简单化</strong>: Agent A의 메모리가 Agent B에 영향을 주지 않으므로, 메모리 관리 코드가 크게 단순화된다.</li>
<li><strong>Cold Start 없음</strong>: Durable Objects는 항상 메모리 상태를 유지한다. Agent가 재시작해도 이전 컨텍스트가 살아 있다.</li>
</ul>
<h3 id="section-2-3-durable-objects의-한계와-이해" tabindex="-1">2-3 Durable Objects의 한계와 이해<a href="#section-2-3-durable-objects%EC%9D%98-%ED%95%9C%EA%B3%84%EC%99%80-%EC%9D%B4%ED%95%B4" class="heading-anchor" aria-label="2-3 Durable Objects의 한계와 이해 항목 링크">#</a></h3>
<p>Durable Objects는 <strong>단일 인스턴스 접근</strong>이 핵심이다:</p>
<pre><code class="language-typescript">// ❌ 잘못된 패턴: 여러 agent가 하나의 DO를 공유
const memory = new AgentMemory(env, { id: 'shared-memory' });

// ✅ 올바른 패턴: Agent마다 고유 ID
const memory = new AgentMemory(env, { id: `agent-${agentId}` });
</code></pre>
<p>이는 Cloudflare의 <strong>co-location 모델</strong> 때문이다. 하나의 DO instance는 하나의 Worker에 co-locate되며, 이 인스턴스에 대한 모든 요청은 같은 데이터센터에서 처리된다.</p>

<h3 id="section-3-2-memory-layer의-계층-구조" tabindex="-1">3-2 Memory Layer의 계층 구조<a href="#section-3-2-memory-layer%EC%9D%98-%EA%B3%84%EC%B8%B5-%EA%B5%AC%EC%A1%B0" class="heading-anchor" aria-label="3-2 Memory Layer의 계층 구조 항목 링크">#</a></h3>
<p>Google ADK의 메모리 시스템은 <strong>세 개의 분리된 계층</strong>으로 설계된다:</p>
<pre><code class="language-python"># google/adk/memory/layered_memory.py (개념적 구조)

class LayeredMemory:
    """
    세 개의 메모리 계층:
    1. Working Memory - 현재 세션의 직접적 컨텍스트 (context window)
    2. Episodic Memory - 과거 경험/대화 (SQLite 기반)
    3. Semantic Memory - 구조화된 지식/사실 (Vector DB 기반)
    """

    def __init__(self, agent_id: str):
        self.working  = WorkingMemory(window_tokens=128_000)
        self.episodic = EpisodicMemory(agent_id, backend="sqlite")
        self.semantic = SemanticMemory(agent_id, backend="vectorize")

    def recall(self, query: str, max_results: int = 10) -> List[MemoryItem]:
        """了三 계층에서 동시에 검색 → fused results"""
        episodic = self.episodic.search(query, max=5)
        semantic = self.semantic.search(query, max=5)

        # Working memory는 항상 전체 포함
        working = self.working.get_all()

        return self._fuse_and_rank(working, episodic, semantic)
</code></pre>

<h3 id="section-4-2-fts5-bm25-벡터-검색을-대체하는-선택" tabindex="-1">4-2 FTS5 BM25: 벡터 검색을 대체하는 선택<a href="#section-4-2-fts5-bm25-%EB%B2%A1%ED%84%B0-%EA%B2%80%EC%83%89%EC%9D%84-%EB%8C%80%EC%B2%B4%ED%95%98%EB%8A%94-%EC%84%A0%ED%83%9D" class="heading-anchor" aria-label="4-2 FTS5 BM25: 벡터 검색을 대체하는 선택 항목 링크">#</a></h3>

<h3 id="section-6-1-데이터-모델" tabindex="-1">6-1 데이터 모델<a href="#section-6-1-%EB%8D%B0%EC%9D%B4%ED%84%B0-%EB%AA%A8%EB%8D%B8" class="heading-anchor" aria-label="6-1 데이터 모델 항목 링크">#</a></h3>
<pre><code class="language-sql">-- 메모리 테이블 설계

    memory_type TEXT NOT NULL CHECK(memory_type IN ('episodic', 'semantic', 'config')),

<h3 id="section-6-2-go-구현체-engram-스타일" tabindex="-1">6-2 Go 구현체 (Engram 스타일)<a href="#section-6-2-go-%EA%B5%AC%ED%98%84%EC%B2%B4-engram-%EC%8A%A4%ED%83%80%EC%9D%BC" class="heading-anchor" aria-label="6-2 Go 구현체 (Engram 스타일) 항목 링크">#</a></h3>
<pre><code class="language-go">// memory/memory.go
package memory

import (
    "database/sql"
    "encoding/json"
    "time"

    _ "github.com/mattn/go-sqlite3"
)

type Memory struct {
    ID         string            `json:"id"`
    Content    string            `json:"content"`
    MemoryType string            `json:"memory_type"`
    Project    string            `json:"project,omitempty"`
    Tags       []string          `json:"tags,omitempty"`
    Metadata   map[string]interface{} `json:"metadata,omitempty"`
    CreatedAt  int64             `json:"created_at"`
    AccessedAt int64             `json:"accessed_at"`
    AccessCount int              `json:"access_count"`
}

type Store struct {
    db *sql.DB
}

func New(dbPath string) (*Store, error) {
    db, err := sql.Open("sqlite3", dbPath)
    if err != nil {
        return nil, err
    }

    if err := initSchema(db); err != nil {
        return nil, err
    }

    return &#x26;Store{db: db}, nil
}

func initSchema(db *sql.DB) error {
    schema := `
    CREATE TABLE IF NOT EXISTS memories (
        id TEXT PRIMARY KEY,
        content TEXT NOT NULL,
        memory_type TEXT NOT NULL,
        project TEXT,
        tags TEXT,
        metadata TEXT,
        created_at INTEGER NOT NULL,
        accessed_at INTEGER NOT NULL,
        access_count INTEGER DEFAULT 0
    );
    CREATE VIRTUAL TABLE IF NOT EXISTS memories_fts USING fts5(content);
    CREATE INDEX IF NOT EXISTS idx_memories_accessed ON memories(accessed_at, memory_type);
    `
    _, err := db.Exec(schema)
    return err
}

func (s *Store) Add(m Memory) error {
    tagsJSON, _ := json.Marshal(m.Tags)
    metaJSON, _ := json.Marshal(m.Metadata)
    now := time.Now().UnixMilli()

    tx, err := s.db.Begin()
    if err != nil {
        return err
    }
    defer tx.Rollback()

    _, err = tx.Exec(`
        INSERT INTO memories (id, content, memory_type, project, tags, metadata, created_at, accessed_at, access_count)
        VALUES (?, ?, ?, ?, ?, ?, ?, ?, 0)`,
        m.ID, m.Content, m.MemoryType, m.Project, string(tagsJSON), string(metaJSON), now, now)
    if err != nil {
        return err
    }

    _, err = tx.Exec(`INSERT INTO memories_fts(rowid, content) VALUES ((SELECT rowid FROM memories WHERE id = ?), ?)`, m.ID, m.Content)
    if err != nil {
        return err
    }

    return tx.Commit()
}

func (s *Store) SearchFTS(query string, project string, limit int) ([]Memory, error) {
    sqlQuery := `SELECT id, content, memory_type, project, tags, metadata, created_at, accessed_at, access_count
                 FROM memories m
                 WHERE memories_fts MATCH ?
                   AND (? = '' OR m.project = ?)
                 ORDER BY bm25(memories_fts, ?) ASC
                 LIMIT ?`

    if err != nil {
        return nil, err
    }

    var results []Memory

<pre><code class="language-python">def rrf_fusion(results_vector, results_fts, k=60):
    """두 검색 결과 집합을 RRF로 통합"""
    scores = {}
    for rank, item in enumerate(results_fts):
        scores[item.id] = scores.get(item.id, 0) + 1 / (k + rank + 1)
    for rank, item in enumerate(results_vector):
        scores[item.id] = scores.get(item.id, 0) + 1 / (k + rank + 1)

    return sorted(scores.items(), key=lambda x: x[1], reverse=True)

<h2 id="section-8-결론-2026년-agent-memory의-lessons-learned" tabindex="-1">8. 결론: 2026년 Agent Memory의 lessons learned<a href="#section-8-%EA%B2%B0%EB%A1%A0-2026%EB%85%84-agent-memory%EC%9D%98-lessons-learned" class="heading-anchor" aria-label="8. 결론: 2026년 Agent Memory의 lessons learned 항목 링크">#</a></h2>
<ol>
<li><strong>Purpose-built storage가 정답</strong>: 하나의 데이터베이스로 모든 것을 해결하려 하지 말라. Episodic/Semantic/Working은 성격이 다르다.</li>
<li><strong>SQLite의復興</strong>: 벡터 DB 과대평가에서 SQLite FTS5로 회귀하는 추세가 있다. BM25는 대부분의 Agent 메모리 검색 시나리오에 적합하다.</li>
<li><strong>Isolation이シンプル화</strong>: Agent별 스토어 분리가 전체 시스템을 크게 단순화한다.</li>
<li><strong>MCP가 표준이 될 것</strong>: Engram의 방향(Agent-agnostic memory)이 산업 표준이 될 가능성이 높다.</li>
<li><strong>Simple is correct</strong>: 복잡한 벡터 파이프라인보다 단순한 BM25 FTS5가 더 자주, 더 정확하게 동작한다.</li>
</ol>
