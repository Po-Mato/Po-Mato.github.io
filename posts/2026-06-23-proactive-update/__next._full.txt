<h3 id="section-2-1-ai-dlc-5단계-상세" tabindex="-1">2.1. AI-DLC 5단계 상세<a href="#section-2-1-ai-dlc-5%EB%8B%A8%EA%B3%84-%EC%83%81%EC%84%B8" class="heading-anchor" aria-label="2.1. AI-DLC 5단계 상세 항목 링크">#</a></h3>
<p>Kiro의 아키텍처와 AWS의 발표를 종합하면, AI-DLC는 다음 5단계로 구성된다:</p>
<p><strong>Phase 1: Spec Engineering (Feature Spec 작성)</strong></p>
<ul>
<li>인간이 Prompt 또는 semi-structured spec을 작성</li>
<li>Kiro Specs 엔진이 논리적 모순, 모호성, 누락을 자동 분석</li>
<li>Property 기반으로 검증 가능한 Spec으로 변환</li>
</ul>
<p><strong>Phase 2: Validation (Spec 품질 검증)</strong></p>
<ul>
<li>Agent가 Spec을 기반으로 Test Oracle 생성</li>
<li>"이 Spec이 의미 있는가?"를 자동 판단 (정확성, 완전성, 일관성)</li>
<li>SWE-bench 스타일의 Benchmark 기반 검증</li>
</ul>
<p><strong>Phase 3: Code Generation + Correctness (코드 생성 및 정확성 검증)</strong></p>
<ul>
<li>Spec을 기반으로 Multi-file 코드 생성</li>
<li><strong>Property-Based Testing</strong>(fuzz testing 유사)으로 단위 테스트가 잡지 못하는 버그 탐지</li>
<li>논리 추론(logical reasoning)으로 비결정성(non-determinism) 감소</li>
</ul>
<p><strong>Phase 4: Release Management (안전한 배포)</strong></p>
<ul>
<li>DevOps Agent Release Management가 PR → Build → Test → Deploy 전 과정을 Agent가 Orchestrate</li>
<li>변경 영향도 분석, 롤백 자동화</li>
</ul>
<p><strong>Phase 5: Continuous Learning (지속적 학습)</strong></p>
<ul>
<li>Agent가 실행 결과를 학습하여 Spec/Test/코드 개선</li>
<li>AWS Context가 Knowledge Graph를 통해 조직 전체의 Agent 지식 공유</li>
</ul>

<h3 id="section-3-1-spec-engine-prompt를-engineering-artifact로" tabindex="-1">3.1. Spec Engine: Prompt를 Engineering Artifact로<a href="#section-3-1-spec-engine-prompt%EB%A5%BC-engineering-artifact%EB%A1%9C" class="heading-anchor" aria-label="3.1. Spec Engine: Prompt를 Engineering Artifact로 항목 링크">#</a></h3>
<p>Kiro의 Spec Engine은 자연어 Prompt를 <strong>구조화된 Feature Spec</strong>으로 변환한다. 이 Spec은 단순한 마크다운이 아니라, 논리적 검증이 가능한 반정형 문서다.</p>
<pre><code class="language-typescript">// Kiro Feature Spec (개념적 구조)
interface FeatureSpec {
  id: string;
  title: string;
  
  // "What" — 의도 명세
  intent: {
    description: string;
    userStory: string;
    acceptanceCriteria: AcceptanceCriteria[];
  };
  
  // "How" — 구현 명세  
  technicalSpec: {
    dataFlow: DataFlow[];
    edgeCases: EdgeCase[];
    invariants: Property[];      // ← 핵심: Property-Based Test 대상
    dependencies: Dependency[];
  };
  
  // "Validate" — 검증 명세
  validation: {
    properties: PropertyAssertion[];  // "모든 입력에 대해 X는 항상 Y를 반환해야 함"
    fuzzScenarios: FuzzConfig[];
    oracleAssertions: OracleAssertion[];
  };
  
  // Kiro가 자동 생성하는 Analysis
  analysis: {
    logicalConsistency: boolean;
    ambiguityWarnings: Warning[];
    completenessScore: number;    // 0-1
    suggestedImprovements: Suggestion[];
  };
}
</code></pre>
<pre><code class="language-typescript">// 실제 Kiro Spec Validation 예시
// 사용자 입력: "사용자가 로그인하면 JWT 토큰을 반환하는 API를 만들어줘"
// Kiro가 분석한 결과:

const specValidation = await kiro.analyzeSpec(`

<h3 id="section-3-2-correctness-engine-all-tests-passed-를-넘어서" tabindex="-1">3.2. Correctness Engine: "All tests passed"를 넘어서<a href="#section-3-2-correctness-engine-all-tests-passed-%EB%A5%BC-%EB%84%98%EC%96%B4%EC%84%9C" class="heading-anchor" aria-label="3.2. Correctness Engine: &#x22;All tests passed&#x22;를 넘어서 항목 링크">#</a></h3>
<p>Kiro의 가장 혁신적인 점은 <strong>Property-Based Testing (PBT)</strong> 이다. 기존 AI 코딩 도구가 생성한 코드의 검증을 "dev가 테스트를 작성한다"에 의존하는 반면, Kiro는 Spec의 Property를 기반으로 자동으로 Fuzz-style 테스트를 생성하고 실행한다.</p>
<pre><code>All Tests Passed ≠ Correct Code

전통적 접근:
  Dev: "이 함수가 작동하는지 3가지 예시로 테스트해볼게"
  → Example-Based Testing: 특정 입력에 대해서만 검증

Kiro 접근:
  Spec: "이 함수는 모든 양의 정수 입력에 대해... 해야 함"
  → Property-Based Testing: 일반 속성(property)을 검증
  → Fuzzing: Infinite random inputs → invariant 유지 검사
</code></pre>
<pre><code class="language-go">// Property-Based Testing 예시 (Go + 빠른 원리 설명)

// 전통적 Example-Based Test:
func TestSort(t *testing.T) {
    input := []int{3, 1, 2}
    result := Sort(input)
    expected := []int{1, 2, 3}
    if !reflect.DeepEqual(result, expected) {
        t.Fail()
    }
}
// → [3,1,2]에 대해서만 검증. [1,1,1]이나 [MAX_INT, -1, 0]은 검증하지 않음.

// Kiro Property-Based Test:
func TestSort_Properties(t *testing.T) {
    // Property 1: 정렬된 배열은 항상 비내림차순
    testing.QuickCheck(func(arr []int) bool {
        sorted := Sort(arr)
        for i := 0; i &#x3C; len(sorted)-1; i++ {
            if sorted[i] > sorted[i+1] {
                return false
            }
        }
        return true
    })
    
    // Property 2: 정렬 전후 원소의 multiset은 동일
    testing.QuickCheck(func(arr []int) bool {
        sorted := Sort(arr)
        return len(sorted) == len(arr) &#x26;&#x26; 
               containsSameElements(sorted, arr)
    })
    
    // Property 3: 정렬은 멱등 (idempotent)
    testing.QuickCheck(func(arr []int) bool {
        sorted := Sort(arr)
        doubleSorted := Sort(sorted)
        return reflect.DeepEqual(sorted, doubleSorted)
    })
}
</code></pre>
<p>이 접근법이 중요한 이유: <strong>LLM이 생성한 코드는 "잘못된 코드가 모든 테스트를 통과"하는 상황(False Positive)이 빈번</strong>하다. Property-Based Testing은 특정 예시가 아닌 일반적인 속성을 검증하므로, LLM의 "테스트에 맞춰진 잘못된 구현"을 탐지할 확률이 훨씬 높다.</p>

AWS Context: Agent를 위한 조직 지식 계층<a href="#section-4-aws-context-agent%EB%A5%BC-%EC%9C%84%ED%95%9C-%EC%A1%B0%EC%A7%81-%EC%A7%80%EC%8B%9D-%EA%B3%84%EC%B8%B5" class="heading-anchor" aria-label="4. AWS Context: Agent를 위한 조직 지식 계층 항목 링크">#</a></h2>

<pre><code>AWS Context Architecture:

│                    Agents                            │
│  (Kiro / Bedrock / Quick / Custom)                   │
├─────────────────────────────────────────────────────┤

<h3 id="section-4-1-agent-context의-진화" tabindex="-1">4.1. Agent Context의 진화<a href="#section-4-1-agent-context%EC%9D%98-%EC%A7%84%ED%99%94" class="heading-anchor" aria-label="4.1. Agent Context의 진화 항목 링크">#</a></h3>
<pre><code>Agent Context Evolution:

Gen 1: Prompt Engineering
  "context": "너는 CS 에이전트야. 이 제품 정보를 참고해..."
  → 수동, 정적, 유지보수 불가

Gen 2: RAG (Retrieval Augmented Generation)
  query → Vector DB → Top-K chunks → LLM
  → 문맥 이해 부족 (단순 검색), 관계 파악 불가

Gen 3: AWS Context (Knowledge Graph)
  query → Graph Query (self-healing path)
  → 관계 기반 검색, Authority 추론, Learning over time
</code></pre>
<p>AWS Context가 기존 RAG와 다른 결정적 차이는 <strong>지식 그래프가 시간에 따라 학습한다</strong>는 점이다:</p>
<pre><code># AWS Context Feedback Loop

for each agent_query:
    # 1. 그래프 탐색으로 최적 경로 찾기
    path = aws_context.navigate(query)
    
    # 2. 결과 반환 및 Agent 응답 생성
    result = agent.execute(path)
    
    # 3. 결과 평가 (authority scoring)
    if user_confirms_result:
        aws_context.boost_path(path)  # 이 경로 가중치 증가
    else:
        aws_context.penalize_path(path)  # 이 경로 가중치 감소
    
    # 4. 새로운 관계 발견 시 그래프 확장
    for discovered_relation in result.new_relations:
        aws_context.add_edge(discovered_relation)
</code></pre>
<p><strong>Edge 케이스 적용</strong>: 초기 RAG 시스템과 달리, "가장 권위 있는 소스"를 자동 식별한다. 예를 들어, 동일한 "refund policy"에 대해 Wiki 문서, Slack 메시지, 이메일이 충돌할 때, AWS Context는 어떤 소스가 가장 신뢰할 만한지 상호작용 피드백을 통해 학습한다.</p>

<h2 id="section-5-aws-continuum-agentic-security의-새로운-패러다임" tabindex="-1">5. AWS Continuum: Agentic Security의 새로운 패러다임<a href="#section-5-aws-continuum-agentic-security%EC%9D%98-%EC%83%88%EB%A1%9C%EC%9A%B4-%ED%8C%A8%EB%9F%AC%EB%8B%A4%EC%9E%84" class="heading-anchor" aria-label="5. AWS Continuum: Agentic Security의 새로운 패러다임 항목 링크">#</a></h2>
<p>Continuum은 AI-DLC의 보안 레이어다. 전통적인 SAST/DAST가 정적인 규칙 기반인 반면, Continuum은 <strong>Agent가 취약점을 발견하고, 검증하고, 우선순위를 정하고, 수정까지 자동화</strong>한다.</p>
<pre><code>Continuum Pipeline:

┌─────────────────────────────────────────────────────────┐
│ Step 1: Discover  (지속적 취약점 스캔)                   │
│  • Agent가 모든 코드베이스, 의존성, 인프라를 스캔        │
│  • 새 취약점(CVE) 발견 시 즉시 Agent Alert               │
│                                                          │
│ Step 2: Validate   (실제 악용 가능성 검증)               │
│  • 모든 취약점이 실제로 악용 가능한지 Agent 시뮬레이션    │
│  • CVSS 점수만으로 판단하지 않고 Exploitability Context  │
│    → "이 취약점은 공개 API가 아니므로 Priority 낮춤"     │
│                                                          │
│ Step 3: Prioritize (비즈니스 맥락 기반 우선순위)          │
│  • 취약점이 위치한 서비스의 중요도, 데이터 민감도 고려   │
│  • "Customer-facing endpoint" > "internal admin panel"   │
│                                                          │
│ Step 4: Remediate  (자동 수정)                           │
│  • Agent가 패치 코드를 생성하고 PR 생성                   │
│  • 롤백 가능성 평가 → "무슨 일이 있어도 이 변경은        │
│    안전하게 되돌릴 수 있어야 함"                          │
│                                                          │
│ Step 5: Verify     (수정 검증)                            │
│  • 패치 적용 후 동일한 공격 벡터로 재테스트               │
│  • 사이드 이펙트 검증: 다른 기능에 영향 없음 확인         │
└─────────────────────────────────────────────────────────┘
</code></pre>
<p>Continuum의 결정적 차별점: <strong>Model-Agnostic + Explainable + Auditable</strong>. 각 단계에서 "왜 이 결정을 내렸는지"에 대한 설명을 생성하고, 모든 결정을 감사 가능한 형태로 저장한다.</p>

<h3 id="section-전략-4-release-management-agent-pipeline" tabindex="-1">전략 4: Release Management Agent Pipeline<a href="#section-%EC%A0%84%EB%9E%B5-4-release-management-agent-pipeline" class="heading-anchor" aria-label="전략 4: Release Management Agent Pipeline 항목 링크">#</a></h3>
<p>DevOps Agent Release Management의 접근법을 차용:</p>
<pre><code class="language-typescript">// AI-DLC Release Pipeline (개념적)
class AIDLCReleasePipeline {
  async execute(spec: FeatureSpec): Promise&#x3C;ReleaseResult> {
    // Step 1: Spec 검증
    const validation = await this.specEngine.validate(spec);
    if (!validation.consistent) throw new SpecInconsistentError(validation.warnings);
    
    // Step 2: 코드 생성
    const code = await this.codeGenerator.generate(spec);
    
    // Step 3: Correctness 검증
    const correctness = await this.correctnessEngine.verify(code, spec.properties);
    if (!correctness.passed) {
      const fixed = await this.selfCorrect(code, correctness.violations);
      // Self-Correction Loop (#047 참고)
      return this.executeWithFix(spec, fixed);
    }
    
    // Step 4: 변경 영향도 분석
    const impact = await this.impactAnalyzer.analyze(code, 
      { depth: 'dependency', includeRollback: true });
    
    // Step 5: 안전 배포
    return this.releaseManager.deploy(code, {
      rolloutStrategy: 'canary',
      autoRollback: impact.hasCriticalPath,
      validationWindowMs: 300_000,  // 5분 모니터링
    });
  }
}
</code></pre>

<h2 id="section-8-결론-ai-dlc는-선택이-아니라-방향이다" tabindex="-1">8. 결론: AI-DLC는 선택이 아니라 방향이다<a href="#section-8-%EA%B2%B0%EB%A1%A0-ai-dlc%EB%8A%94-%EC%84%A0%ED%83%9D%EC%9D%B4-%EC%95%84%EB%8B%88%EB%9D%BC-%EB%B0%A9%ED%96%A5%EC%9D%B4%EB%8B%A4" class="heading-anchor" aria-label="8. 결론: AI-DLC는 선택이 아니라 방향이다 항목 링크">#</a></h2>
<p>AWS Summit NY 2026의 메시지는 명확하다: <strong>"더 이상 Agent를 쓸지 말지 고민할 때가 아니라, Agent와 어떻게 함께 일할지 설계할 때다."</strong></p>
<p>Southwest Airlines가 2,700명의 개발자를 AI-DLC로 전환하고, AWS가 Continuum/Context/Kiro라는 전방위 서비스를 출시한 것은 우연이 아니다. 소프트웨어 공학은 다음 단계로 진화하고 있다:</p>
<ol>
<li><strong>Spec이 코드보다 중요해진다</strong>: Agent가 Spec을 이해하고 검증하는 시대</li>
<li><strong>Testing이 Verification으로 진화한다</strong>: Example-Based → Property-Based</li>
<li><strong>보안이 게이트에서 지속적 프로세스로</strong>: Continuum의 Agentic Security</li>
<li><strong>Context가 Competitive Advantage가 된다</strong>: AWS Context가 보여주는 지식 그래프의 힘</li>
<li><strong>조직 구조가 변화한다</strong>: Engineer → AI-DLC Engineer</li>
</ol>
<p>AI-DLC는 단순히 "코드를 빨리 짜는 방법"이 아니다. <strong>소프트웨어의 품질, 보안, 유지보수성을 Agent-assisted Engineering Workflow로 격상시키는 패러다임 전환</strong>이다. 2026년 하반기, Enterprise 조직이 이 방향으로 움직이지 않는다면, 경쟁력의 격차는 점점 더 벌어질 것이다.</p>
