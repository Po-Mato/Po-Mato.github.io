11:T3294,<h1>클라우드 네이티브 환경에 AI 에이전트를 통합하는 설계</h1>
<p>AI 에이전트가 만든 변경을 운영 환경에 연결하려면 생성 단계와 검증·승인·배포 단계를 구분해야 합니다. <a href="https://www.gartner.com/en/newsroom/press-releases/2021-11-10-gartner-says-cloud-will-be-the-centerpiece-of-new-digital-experiences">Gartner의 2021년 발표</a>는 <strong>2025년까지</strong> 신규 디지털 워크로드의 95% 이상이 클라우드 네이티브 플랫폼에 배포될 것으로 예측했습니다. 이는 2026년 실측치가 아닙니다. 이 글은 시장 예측의 달성 여부 대신 검증 경계를 설계하고 실행해 보는 데 집중합니다.</p>
<h2 id="section-cloud-native의-완성-플랫폼-엔지니어링" tabindex="-1">Cloud-Native의 완성: 플랫폼 엔지니어링<a href="#section-cloud-native%EC%9D%98-%EC%99%84%EC%84%B1-%ED%94%8C%EB%9E%AB%ED%8F%BC-%EC%97%94%EC%A7%80%EB%8B%88%EC%96%B4%EB%A7%81" class="heading-anchor" aria-label="Cloud-Native의 완성: 플랫폼 엔지니어링 항목 링크">#</a></h2>
<p>클라우드 네이티브는 이제 표준이 되었습니다. 하지만 규모가 커질수록 복잡성은 폭발적으로 증가합니다. 이를 해결하기 위해 플랫폼 엔지니어링 팀은 다음과 같은 핵심 전략을 시행하고 있습니다.</p>
<ol>
<li><strong>API 표준화 및 규격화</strong>: 개발자가 비즈니스 로직에 집중할 수 있도록 추상화 계층을 제공합니다.</li>
<li><strong>자동화된 보안 및 거버넌스</strong>: 모든 프로젝트는 CI/CD 파이프라인에서 보안 스캔이 자동 수행되어야 하며, <code>git</code> 리포지토리에 연결되어 변경 이력이 투명하게 관리되어야 합니다.</li>
</ol>
<h2 id="section-agentic-ai-시대의-아키텍처-변화" tabindex="-1">Agentic AI 시대의 아키텍처 변화<a href="#section-agentic-ai-%EC%8B%9C%EB%8C%80%EC%9D%98-%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98-%EB%B3%80%ED%99%94" class="heading-anchor" aria-label="Agentic AI 시대의 아키텍처 변화 항목 링크">#</a></h2>
<p>코드 생성 자동화의 비용·속도 효과는 작업과 검증 비용에 따라 달라집니다. 생성 결과를 검토 없이 배포하지 않도록 입력 정책, 검증 결과, 승인과 배포 권한을 분리해야 합니다.</p>
<h3 id="section-아키텍처-예시-ai-에이전트-통합-파이프라인" tabindex="-1">아키텍처 예시: AI 에이전트 통합 파이프라인<a href="#section-%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98-%EC%98%88%EC%8B%9C-ai-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8-%ED%86%B5%ED%95%A9-%ED%8C%8C%EC%9D%B4%ED%94%84%EB%9D%BC%EC%9D%B8" class="heading-anchor" aria-label="아키텍처 예시: AI 에이전트 통합 파이프라인 항목 링크">#</a></h3>

<h3 id="section-아키텍트의-역할" tabindex="-1">아키텍트의 역할<a href="#section-%EC%95%84%ED%82%A4%ED%85%8D%ED%8A%B8%EC%9D%98-%EC%97%AD%ED%95%A0" class="heading-anchor" aria-label="아키텍트의 역할 항목 링크">#</a></h3>
<p>이제 아키텍트는 단순히 시스템 구조를 그리는 사람이 아닙니다. **'AI가 생성한 코드와 아키텍처를 검증하고 제어하는 오케스트레이터'**가 되어야 합니다. AI를 신뢰하되, 검증 파이프라인은 플랫폼 엔지니어가 직접 설계하고 관리해야 합니다.</p>
<h2 id="section-로컬-실습-검증을-통과해도-승인-전에는-멈추기" tabindex="-1">로컬 실습: 검증을 통과해도 승인 전에는 멈추기<a href="#section-%EB%A1%9C%EC%BB%AC-%EC%8B%A4%EC%8A%B5-%EA%B2%80%EC%A6%9D%EC%9D%84-%ED%86%B5%EA%B3%BC%ED%95%B4%EB%8F%84-%EC%8A%B9%EC%9D%B8-%EC%A0%84%EC%97%90%EB%8A%94-%EB%A9%88%EC%B6%94%EA%B8%B0" class="heading-anchor" aria-label="로컬 실습: 검증을 통과해도 승인 전에는 멈추기 항목 링크">#</a></h2>
<p>목표는 입력 검증 → 승인 확인 → 모의 배포 기록의 분기를 직접 확인하는 것입니다. <strong>실제 AI 호출·보안 스캔·클라우드 배포는 수행하지 않습니다.</strong> 네트워크나 API 키가 필요 없고, 파일에는 배포 결과를 쓰지 않습니다. 결과는 터미널의 JSON 한 줄로만 출력합니다.</p>
<p>Python 3.10 이상과 터미널이 필요합니다. 이 글의 로컬 재현 환경은 Python 3.14.3입니다. 추가 패키지는 없습니다. 별도 실습 폴더를 만들고 아래 코드를 <code>pipeline-lab.py</code>로 저장하세요. <a href="/examples/pipeline-lab.py">같은 Python 파일 다운로드</a>도 제공합니다.</p>
<pre><code class="language-python">"""로컬 교육용 검증 파이프라인. 네트워크 요청과 실제 배포는 하지 않는다."""
import argparse
import json
from pathlib import Path


def report(status, message, exit_code):
    print(json.dumps({"status": status, "message": message}, ensure_ascii=False))
    return exit_code


def main():
    parser = argparse.ArgumentParser(description="입력 검증과 승인 분기 실습")
    parser.add_argument("request", type=Path)
    parser.add_argument("--approve", action="store_true", help="모의 배포에 동의")
    args = parser.parse_args()
    try:
        plan = json.loads(args.request.read_text(encoding="utf-8"))
    except (OSError, UnicodeError, json.JSONDecodeError):
        return report("invalid", "입력 파일을 읽거나 JSON으로 해석할 수 없습니다.", 2)

    fields = {"service", "environment", "tests_passed"}
    if not isinstance(plan, dict) or set(plan) != fields:
        return report("invalid", "service, environment, tests_passed만 필요합니다.", 2)
    if plan["service"] != "demo-api" or plan["environment"] != "staging":
        return report("rejected", "demo-api의 staging만 허용합니다.", 2)
    if plan["tests_passed"] is not True:
        return report("rejected", "tests_passed는 JSON true여야 합니다.", 2)
    if not args.approve:
        return report("approval_required", "검토 후 --approve로 다시 실행하세요.", 3)

    print(json.dumps({
        "status": "simulated", "service": plan["service"],
        "environment": plan["environment"], "deployed": False,
    }, ensure_ascii=False))
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
</code></pre>
<h3 id="section-1-입력-준비" tabindex="-1">1. 입력 준비<a href="#section-1-%EC%9E%85%EB%A0%A5-%EC%A4%80%EB%B9%84" class="heading-anchor" aria-label="1. 입력 준비 항목 링크">#</a></h3>
<p>같은 폴더에 <code>request.json</code>을 만들고 다음 내용을 저장합니다. 문자열 <code>"true"</code>가 아니라 JSON 불리언 <code>true</code>를 사용합니다.</p>
<pre><code class="language-json">{"service":"demo-api","environment":"staging","tests_passed":true}
</code></pre>
<p>실습 정책은 정확히 세 필드, 서비스 <code>demo-api</code>, 환경 <code>staging</code>, 검사 결과 <code>true</code>만 허용합니다. 예시의 <code>tests_passed</code>는 사용자가 작성한 값입니다. 실제 테스트 통과나 코드 안전성을 증명하지 않습니다.</p>
<h3 id="section-2-승인-없이-실행" tabindex="-1">2. 승인 없이 실행<a href="#section-2-%EC%8A%B9%EC%9D%B8-%EC%97%86%EC%9D%B4-%EC%8B%A4%ED%96%89" class="heading-anchor" aria-label="2. 승인 없이 실행 항목 링크">#</a></h3>

<h3 id="section-3-내용을-검토한-뒤-모의-승인" tabindex="-1">3. 내용을 검토한 뒤 모의 승인<a href="#section-3-%EB%82%B4%EC%9A%A9%EC%9D%84-%EA%B2%80%ED%86%A0%ED%95%9C-%EB%92%A4-%EB%AA%A8%EC%9D%98-%EC%8A%B9%EC%9D%B8" class="heading-anchor" aria-label="3. 내용을 검토한 뒤 모의 승인 항목 링크">#</a></h3>
<pre><code class="language-sh">python3 pipeline-lab.py request.json --approve
</code></pre>
<p>종료 코드 <code>0</code>과 다음 기록이 나옵니다. <code>deployed: false</code>는 실제 배포가 없었다는 뜻입니다.</p>
<pre><code class="language-json">{"status": "simulated", "service": "demo-api", "environment": "staging", "deployed": false}
</code></pre>
<h3 id="section-4-정책-위반과-잘못된-입력-재현" tabindex="-1">4. 정책 위반과 잘못된 입력 재현<a href="#section-4-%EC%A0%95%EC%B1%85-%EC%9C%84%EB%B0%98%EA%B3%BC-%EC%9E%98%EB%AA%BB%EB%90%9C-%EC%9E%85%EB%A0%A5-%EC%9E%AC%ED%98%84" class="heading-anchor" aria-label="4. 정책 위반과 잘못된 입력 재현 항목 링크">#</a></h3>
<p><code>request.json</code>의 <code>environment</code>를 <code>production</code>으로 바꾸고 같은 승인 명령을 실행합니다. 승인 플래그가 있어도 종료 코드 <code>2</code>로 거절합니다.</p>
<pre><code class="language-json">{"status": "rejected", "message": "demo-api의 staging만 허용합니다."}
</code></pre>
<p>다시 <code>staging</code>으로 돌리고 <code>tests_passed</code>를 <code>false</code>, <code>1</code>, <code>"true"</code> 중 하나로 바꿔 보세요. 모두 종료 코드 <code>2</code>이며 <code>tests_passed는 JSON true여야 합니다.</code>가 표시됩니다. 필드를 빼거나 추가하면 입력 형식 오류가 나고, 잘못된 JSON 또는 없는 파일도 종료 코드 <code>2</code>로 끝납니다. 거절 시에는 <code>simulated</code> 기록이 나오지 않아야 합니다.</p>
<p>macOS/Linux 터미널에서는 각 명령 <strong>바로 다음에</strong> <code>echo $?</code>, PowerShell에서는 <code>$LASTEXITCODE</code>로 종료 코드를 확인할 수 있습니다. 다른 명령을 먼저 실행하면 그 명령의 종료 상태가 표시됩니다.</p>
<h3 id="section-운영-설계로-옮길-때의-경계" tabindex="-1">운영 설계로 옮길 때의 경계<a href="#section-%EC%9A%B4%EC%98%81-%EC%84%A4%EA%B3%84%EB%A1%9C-%EC%98%AE%EA%B8%B8-%EB%95%8C%EC%9D%98-%EA%B2%BD%EA%B3%84" class="heading-anchor" aria-label="운영 설계로 옮길 때의 경계 항목 링크">#</a></h3>
<p><code>--approve</code>는 사용자의 명시적 선택을 연습하는 플래그이며 승인자의 신원·권한을 인증하지 않습니다. 누구나 플래그를 붙일 수 있으므로 운영 승인 장치로 사용하면 안 됩니다. 실제 시스템에서는 검사 결과를 신뢰할 수 있는 실행에서 얻고, 승인한 변경의 식별자와 배포할 산출물이 같은지 확인하며, 승인자 권한·거절·타임아웃·배포 실패·감사 기록을 별도로 설계해야 합니다.</p>
<p>이 실습은 검증과 승인의 <strong>순서와 실패 분기</strong>만 가르칩니다. 카나리 트래픽 전환, 취약점 탐지, 샌드박스, 롤백은 구현하지 않습니다. <a href="/posts/2026-08-28-proactive-update/">8월 28일의 생성·검사 흐름</a>과 비교하면, 승인 주석만 있는 흐름과 명시적으로 멈추는 분기의 차이를 볼 수 있습니다.</p>
<p>정리는 이번에 만든 <code>pipeline-lab.py</code>와 <code>request.json</code> 두 파일만 삭제하면 됩니다. 설치 패키지나 외부 자원은 생성하지 않습니다.</p>
