19:T79fa,<h2 id="section-1-들어가며-에이전트가-프로덕션에-도달하면-생기는-일" tabindex="-1">1. 들어가며: 에이전트가 프로덕션에 도달하면 생기는 일<a href="#section-1-%EB%93%A4%EC%96%B4%EA%B0%80%EB%A9%B0-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%EA%B0%80-%ED%94%84%EB%A1%9C%EB%8D%95%EC%85%98%EC%97%90-%EB%8F%84%EB%8B%AC%ED%95%98%EB%A9%B4-%EC%83%9D%EA%B8%B0%EB%8A%94-%EC%9D%BC" class="heading-anchor" aria-label="1. 들어가며: 에이전트가 프로덕션에 도달하면 생기는 일 항목 링크">#</a></h2>
<p>AI 에이전트를 배포하는 것은 비교적 쉽습니다. 단일 툴 호출을 LLM에 위임하는 간단한 에이전트는 하루 만에 만들 수 있습니다. 하지만 그 에이전트가 <strong>프로덕션에서 7x24시간 운영되기 시작하면</strong> 상황이 달라집니다.</p>
<p><strong>사례 1.</strong> 금융 서비스 팀이 포트폴리오 매니저를 위한 리서치 요약 에이전트를 배포했습니다. 체인은 검색 에이전트 → 요약 LLM → 규정 준수 검증 에이전트로 구성되었습니다. 기존 APM(Application Performance Monitoring) 스택으로는 지연 시간과 에러율만 확인할 수 있었습니다. 일주일 후, 규정 준수 팀이 아침에 세 건의 규정 위반을 발견했습니다. APM 대시보드는 여전히 초록불이었습니다.</p>
<p><strong>사례 2.</strong> 고객 지원 에이전트가 갑자기 이전과 다른 의사결정을 내리기 시작했습니다. LLM 공급자의 모델이 사이드 채널로 업데이트되면서 reasoning 경로가 바뀌었고, 동일한 프롬프트가 다른 툴 체인을 타기 시작했습니다. 문제를 발견한 시점은 사용자 complaints가 쌓이고 난 3일 후였습니다.</p>
<p>이러한 사례의 공통점은 무엇일까요? <strong>기존의 관측성 스택으로는 AI 에이전트의 의사결정 품질을 추적할 수 없다</strong>는 것입니다. 로그, 메트릭, 에러율만으로는 에이전트가 <strong>올바른 결정을 내렸는지</strong>, 그 결정이 <strong>시간이 지남에 따라 개선되고 있는지 악화되고 있는지</strong>를 알 수 없습니다.</p>
<p>이 문제는 단순한 기술적 결함이 아닙니다. 2026년 6월 현재, Microsoft Build 2026에서는 Azure Foundry에서 에이전트 옵저버빌리티가 GA를 맞았고, Coralogix는 AI 옵저버빌리티를 위해 2억 달러 Series F를 조달했습니다. 시장이 이 주제에 베팅하고 있습니다.</p>
<p>이 글에서는 AI Agent Observability의 아키텍처를 세 가지 레이어로 분해합니다:</p>
<ol>
<li><strong>데이터 플레인 (Telemetry Layer)</strong> — OpenTelemetry가 커버하는 범위와 한계</li>
<li><strong>컨트롤 플레인 (Evaluation &#x26; Control Layer)</strong> — 평가, 안전, 정책 적용이 필요한 이유</li>
<li><strong>비즈니스 플레인 (ROI Layer)</strong> — CFO에게 에이전트의 가치를 증명하는 방법</li>
</ol>

<h2 id="section-2-전통적-apm이-실패하는-이유" tabindex="-1">2. 전통적 APM이 실패하는 이유<a href="#section-2-%EC%A0%84%ED%86%B5%EC%A0%81-apm%EC%9D%B4-%EC%8B%A4%ED%8C%A8%ED%95%98%EB%8A%94-%EC%9D%B4%EC%9C%A0" class="heading-anchor" aria-label="2. 전통적 APM이 실패하는 이유 항목 링크">#</a></h2>
<p>전통적인 소프트웨어는 **결정론적(Deterministic)**입니다. 동일한 입력 → 동일한 출력 → 동일한 코드 경로. 따라서 200 OK / 500 Error라는 이분법적 상태 확인이 유효했습니다.</p>
<p>에이전트는 **비결정론적(Non-Deterministic)**입니다. 동일한 프롬프트가 오늘은 세 가지 툴 경로를 타고, 내일은 모델 업데이트로 네 번째 경로를 탈 수 있습니다. LLM 호출 자체가 확률적(stochastic)이며, 툴 선택도 모델의 reasoning에 의존합니다.</p>
<pre><code>// 전통적 APM이 보는 에이전트
// Latency: 2.3s, Status: 200 OK, Error: none

// 실제로 일어난 일
// - 검색 에이전트가 잘못된 데이터 소스 선택 (정확도 42%)
// - 요약 LLM이 문서에 없는 통계를 생성 (환각)
// - 규정 준수 에이전트가 forward-looking statement 위반을 놓침 (missed)
</code></pre>
<p>이것이 **"인스트루먼테이션 블라인드 스팟(Instrumentation Blind Spot)"**입니다. 에러율, 지연 시간, 스루풋은 정상이지만, 에이전트의 <strong>의사결정 품질</strong>은 확인할 수 없습니다.</p>

<h2 id="section-3-데이터-플레인-opentelemetry가-커버하는-범위" tabindex="-1">3. 데이터 플레인: OpenTelemetry가 커버하는 범위<a href="#section-3-%EB%8D%B0%EC%9D%B4%ED%84%B0-%ED%94%8C%EB%A0%88%EC%9D%B8-opentelemetry%EA%B0%80-%EC%BB%A4%EB%B2%84%ED%95%98%EB%8A%94-%EB%B2%94%EC%9C%84" class="heading-anchor" aria-label="3. 데이터 플레인: OpenTelemetry가 커버하는 범위 항목 링크">#</a></h2>
<p>OpenTelemetry는 이 문제의 <strong>데이터 계층</strong>을 해결합니다. 2026년 현재 OpenTelemetry GenAI SIG는 AI 워크로드 전용 시맨틱 컨벤션을 정의했으며, 이는 세 가지 핵심 속성을 제공합니다:</p>
<h3 id="section-3-1-벤더-중립성-vendor-neutrality" tabindex="-1">3.1 벤더 중립성(Vendor Neutrality)<a href="#section-3-1-%EB%B2%A4%EB%8D%94-%EC%A4%91%EB%A6%BD%EC%84%B1-vendor-neutrality" class="heading-anchor" aria-label="3.1 벤더 중립성(Vendor Neutrality) 항목 링크">#</a></h3>
<p>한 번 인스트루먼트하면 어떤 백엔드로도 내보낼 수 있습니다. LLM 공급자를 교체해도 속성 이름, 트레이스 구조, 대시보드가 일관됩니다.</p>

<h3 id="section-3-2-에이전트-계층-전체의-분산-트레이싱" tabindex="-1">3.2 에이전트 계층 전체의 분산 트레이싱<a href="#section-3-2-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8-%EA%B3%84%EC%B8%B5-%EC%A0%84%EC%B2%B4%EC%9D%98-%EB%B6%84%EC%82%B0-%ED%8A%B8%EB%A0%88%EC%9D%B4%EC%8B%B1" class="heading-anchor" aria-label="3.2 에이전트 계층 전체의 분산 트레이싱 항목 링크">#</a></h3>
<p>OpenTelemetry 트레이스는 사용자 요청 → 오케스트레이터 → 서브 에이전트 → 툴 호출 → LLM 호출의 전체 호출 그래프를 캡처합니다. 각 단계는 구조화된 속성을 가진 스팬(span)이 됩니다.</p>
<h3 id="section-3-3-통합-파이프라인" tabindex="-1">3.3 통합 파이프라인<a href="#section-3-3-%ED%86%B5%ED%95%A9-%ED%8C%8C%EC%9D%B4%ED%94%84%EB%9D%BC%EC%9D%B8" class="heading-anchor" aria-label="3.3 통합 파이프라인 항목 링크">#</a></h3>
<p>OTel Collector는 메트릭, 트레이스, 로그를 단일 파이프라인에서 처리합니다. LLM 호출의 레이턴시 스파이크가 네트워크 파티션 때문인지, 모델 프로바이더의 레이트 리밋 때문인지 동일한 트레이스 컨텍스트 내에서 추적할 수 있습니다.</p>
<h3 id="section-3-4-opentelemetry가-커버하지-못하는-것" tabindex="-1">3.4 OpenTelemetry가 커버하지 못하는 것<a href="#section-3-4-opentelemetry%EA%B0%80-%EC%BB%A4%EB%B2%84%ED%95%98%EC%A7%80-%EB%AA%BB%ED%95%98%EB%8A%94-%EA%B2%83" class="heading-anchor" aria-label="3.4 OpenTelemetry가 커버하지 못하는 것 항목 링크">#</a></h3>
<p>그러나 OpenTelemetry는 근본적인 한계가 있습니다. **"무슨 일이 일어났는가(what happened)"**는 캡처하지만, **"그것이 괜찮은가(was it good)"**는 평가하지 않습니다.</p>

<h2 id="section-4-컨트롤-플레인-평가와-제어의-아키텍처" tabindex="-1">4. 컨트롤 플레인: 평가와 제어의 아키텍처<a href="#section-4-%EC%BB%A8%ED%8A%B8%EB%A1%A4-%ED%94%8C%EB%A0%88%EC%9D%B8-%ED%8F%89%EA%B0%80%EC%99%80-%EC%A0%9C%EC%96%B4%EC%9D%98-%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98" class="heading-anchor" aria-label="4. 컨트롤 플레인: 평가와 제어의 아키텍처 항목 링크">#</a></h2>
<p>Microsoft Foundry의 Build 2026 발표는 이 간극을 정확히 메웁니다. Foundry는 에이전트 옵저버빌리티를 <strong>네 가지 기능</strong>으로 정의합니다:</p>
<ol>
<li><strong>Trace</strong> — 모든 단계의 엔드투엔드 텔레메트리</li>
<li><strong>Evaluate</strong> — 단일/다중 턴에서의 품질 및 안전 스코어링</li>
<li><strong>Monitor</strong> — Azure Monitor를 통한 실시간 이슈 탐지</li>
<li><strong>Optimize</strong> — 프로덕션 신호를 증거 기반 에이전트 개선으로 전환</li>
</ol>
<h3 id="section-4-1-trace-evaluate-연결" tabindex="-1">4.1 Trace → Evaluate 연결<a href="#section-4-1-trace-evaluate-%EC%97%B0%EA%B2%B0" class="heading-anchor" aria-label="4.1 Trace → Evaluate 연결 항목 링크">#</a></h3>
<p>텔레메트리만으로는 충분하지 않습니다. Foundry의 핵심 혁신은 <strong>Trace를 Evaluate에 직접 연결</strong>하는 점입니다. 즉, 캡처한 트레이스를 런타임에 평가하여 스코어를 할당합니다.</p>
<pre><code class="language-typescript">// 의사 코드: Foundry Agent Observability Trace → Evaluate 파이프라인

  metrics: {
    taskSuccess: { weight: 0.5 },

    safety: { weight: 0.2 },
    latencyCostEfficiency: { weight: 0.1 },
  },
});

// Production 트레이스를 실시간 평가
const trace = await telemetry.getTrace(agentCallId);

<h3 id="section-4-2-multi-turn-evaluation" tabindex="-1">4.2 Multi-Turn Evaluation<a href="#section-4-2-multi-turn-evaluation" class="heading-anchor" aria-label="4.2 Multi-Turn Evaluation 항목 링크">#</a></h3>
<p>단일 턴 평가는 장기 컨텍스트에서만 발생하는 실패 모드를 놓칩니다:</p>
<ul>
<li>컨텍스트 누적으로 인한 톤 변화 (tone drift)</li>
<li>대화 초기의 목표를 잃어버리는 현상 (goal drift)</li>
<li>긴 대화에서의 모순 발생 (contradiction)</li>
<li>안전 회귀 (safety regression)</li>
</ul>
<p>Multi-turn 평가는 전체 대화를 하나의 평가 단위로 취급하여 이러한 복합 실패를 감지합니다.</p>
<h3 id="section-4-3-rubric-evaluator" tabindex="-1">4.3 Rubric Evaluator<a href="#section-4-3-rubric-evaluator" class="heading-anchor" aria-label="4.3 Rubric Evaluator 항목 링크">#</a></h3>
<p>"좋은(good)"의 기준은 에이전트마다 다릅니다. 벤더 이력 에이전트에게 좋은 것과 고객 지원 에이전트에게 좋은 것은 다릅니다.</p>
<p>Rubric Evaluator는 에이전트의 의도된 행동에서 컨텍스트 인식 평가 기준을 <strong>자동 생성</strong>합니다:</p>

<h3 id="section-4-4-지능형-트레이스-샘플링" tabindex="-1">4.4 지능형 트레이스 샘플링<a href="#section-4-4-%EC%A7%80%EB%8A%A5%ED%98%95-%ED%8A%B8%EB%A0%88%EC%9D%B4%EC%8A%A4-%EC%83%98%ED%94%8C%EB%A7%81" class="heading-anchor" aria-label="4.4 지능형 트레이스 샘플링 항목 링크">#</a></h3>
<p>모든 프로덕션 트레이스를 평가하는 것은 낭비이고, 아무것도 평가하지 않는 것은 위험합니다. Foundry의 Intelligent Trace Sampling은 <strong>신호가 가장 풍부한 상호작용</strong>을 선별하여 평가합니다. 중요한 트레이스(고위험 쿼리, 예외 경로, 장기 대화)는 100% 샘플링하고, 일반적인 트레이스는 통계적 샘플링합니다.</p>

<h2 id="section-5-실전-패턴-에이전트-옵저버빌리티-구축하기" tabindex="-1">5. 실전 패턴: 에이전트 옵저버빌리티 구축하기<a href="#section-5-%EC%8B%A4%EC%A0%84-%ED%8C%A8%ED%84%B4-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8-%EC%98%B5%EC%A0%80%EB%B2%84%EB%B9%8C%EB%A6%AC%ED%8B%B0-%EA%B5%AC%EC%B6%95%ED%95%98%EA%B8%B0" class="heading-anchor" aria-label="5. 실전 패턴: 에이전트 옵저버빌리티 구축하기 항목 링크">#</a></h2>
<p>이론적인 아키텍처를 실제 코드로 구현해 보겠습니다.</p>
<h3 id="section-5-1-기본-구조-telemetry-bridge" tabindex="-1">5.1 기본 구조: Telemetry Bridge<a href="#section-5-1-%EA%B8%B0%EB%B3%B8-%EA%B5%AC%EC%A1%B0-telemetry-bridge" class="heading-anchor" aria-label="5.1 기본 구조: Telemetry Bridge 항목 링크">#</a></h3>
<pre><code class="language-python">"""
Agent Observability Bridge Pattern
OTel 텔레메트리를 캡처하여 평가 파이프라인에 전달
"""

from opentelemetry import trace
from opentelemetry.semconv.ai import SpanAttributes
from dataclasses import dataclass, field
from typing import Optional
import json


@dataclass
class AgentDecision:
    """에이전트의 단일 의사결정을 기록하는 구조체"""
    step_id: str
    agent_name: str
    tool_chosen: str
    tool_input: dict
    tool_output: Optional[dict] = None
    latency_ms: float = 0.0
    token_cost: float = 0.0
    confidence_score: Optional[float] = None
    was_recovered: bool = False  # fallback 경로 진입 여부


class ObservableAgent:
    """
    ObservableAgent 데코레이터 패턴:
    모든 의사결정을 OTel 스팬 + 평가 큐에 기록
    """

    def __init__(self, agent_name: str, evaluator=None):
        self.agent_name = agent_name
        self.tracer = trace.get_tracer(agent_name)
        self.evaluator = evaluator
        self.decisions: list[AgentDecision] = []

    def record_decision(self, decision: AgentDecision):
        """의사결정을 OTel 스팬과 평가 큐에 동시 기록"""
        with self.tracer.start_as_current_span(f"agent.{decision.agent_name}") as span:
            span.set_attribute("agent.name", decision.agent_name)
            span.set_attribute("agent.step_id", decision.step_id)
            span.set_attribute("agent.tool_chosen", decision.tool_chosen)
            span.set_attribute("agent.latency_ms", decision.latency_ms)
            span.set_attribute("agent.token_cost", decision.token_cost)
            span.set_attribute("agent.was_recovered", decision.was_recovered)

            # 평가 큐에 추가 (비동기 처리)
            self.decisions.append(decision)

            if decision.confidence_score is not None:
                span.set_attribute(
                    "agent.confidence_score",
                    decision.confidence_score
                )

    async def evaluate_session(self, session_id: str) -> dict:
        """세션 종료 후 전체 의사결정 체인 평가"""
        if not self.evaluator:
            return {"error": "no evaluator configured"}

        return await self.evaluator.evaluate_chain(
            session_id=session_id,
            decisions=self.decisions,
        )
</code></pre>
<h3 id="section-5-2-평가자-구현-multi-turn-chain-evaluator" tabindex="-1">5.2 평가자 구현: Multi-Turn Chain Evaluator<a href="#section-5-2-%ED%8F%89%EA%B0%80%EC%9E%90-%EA%B5%AC%ED%98%84-multi-turn-chain-evaluator" class="heading-anchor" aria-label="5.2 평가자 구현: Multi-Turn Chain Evaluator 항목 링크">#</a></h3>
<pre><code class="language-python">"""
Multi-turn 평가자: 전체 대화 체인에서 복합 실패 모드 감지
"""


class MultiTurnChainEvaluator:
    """
    단일 턴 평가가 놓치는 복합 실패를 감지:
    - Goal drift: 초기 목표와 최종 결과의 정렬도
    - Tone drift: 톤 일관성 변화율
    - Contradiction: 이전 발언과의 모순 빈도
    """

    def __init__(self, llm_client):
        self.llm = llm_client

    async def evaluate_chain(
        self,
        session_id: str,
        decisions: list[AgentDecision],
    ) -> dict:
        goal_alignment = await self._measure_goal_alignment(decisions)
        tone_consistency = await self._measure_tone_consistency(decisions)
        contradictions = await self._detect_contradictions(decisions)
        safety_score = await self._check_safety_compliance(decisions)

        return {
            "session_id": session_id,
            "overall_score": (
                goal_alignment * 0.35
                + tone_consistency * 0.15
                + (1 - contradictions) * 0.25
                + safety_score * 0.25
            ),
            "goal_alignment": goal_alignment,
            "tone_consistency": tone_consistency,
            "contradiction_rate": contradictions,
            "safety_score": safety_score,
            "decision_count": len(decisions),
            "total_latency_ms": sum(
                d.latency_ms for d in decisions
            ),
            "total_token_cost": sum(
                d.token_cost for d in decisions
            ),
            "recovery_rate": sum(
                1 for d in decisions if d.was_recovered
            ) / len(decisions) if decisions else 0,
        }

    async def _measure_goal_alignment(
        self, decisions: list[AgentDecision]
    ) -> float:
        """첫 번째 결정의 목적과 최종 결정의 정렬도 측정"""
        if len(decisions) &#x3C; 2:
            return 1.0
        first_goal = decisions[0].tool_input.get("goal", "")
        final_output = decisions[-1].tool_output
        # LLM 기반 정렬도 평가 (생략: 실제 구현은 LLM 호출)
        return 0.92  # 예시 반환값
</code></pre>
<h3 id="section-5-3-가드레일-통합-telemetry-action-loop" tabindex="-1">5.3 가드레일 통합: Telemetry → Action Loop<a href="#section-5-3-%EA%B0%80%EB%93%9C%EB%A0%88%EC%9D%BC-%ED%86%B5%ED%95%A9-telemetry-action-loop" class="heading-anchor" aria-label="5.3 가드레일 통합: Telemetry → Action Loop 항목 링크">#</a></h3>
<p>텔레메트리만으로는 부족합니다. 평가 결과를 바탕으로 <strong>실시간 제어</strong>가 가능해야 합니다:</p>
<pre><code class="language-python">"""
Observability → Guardrail → Action 파이프라인
"""


class GuardrailEnforcementLoop:
    """
    프로덕션 트레이스 평가 결과를 즉시 액션으로 전환:
    - Safety threshold 초과 → 즉시 차단
    - Quality threshold 미달 → 재시도 또는 fallback
    - Cost anomaly 감지 → 모델 다운그레이드
    """

    def __init__(self, threshold: float = 0.6):
        self.threshold = threshold
        self.action_log: list[dict] = []

    async def process_evaluation(
        self, session_id: str, eval_result: dict
    ) -> str:
        score = eval_result.get("overall_score", 1.0)

        if eval_result.get("safety_score", 1.0) &#x3C; self.threshold:
            action = self._block_session(session_id, eval_result)
        elif score &#x3C; self.threshold:
            action = self._trigger_fallback(
                session_id, eval_result
            )
        else:
            action = self._pass_through(session_id, eval_result)

        self.action_log.append({
            "session_id": session_id,
            "score": score,
            "action": action["type"],
            "timestamp": "2026-06-06T07:00:00Z",
        })
        return action["type"]

    def _block_session(self, session_id: str,
                       eval_result: dict) -> dict:
        return {
            "type": "BLOCK",
            "reason": f"Safety threshold: {eval_result['safety_score']}",
        }

    def _trigger_fallback(self, session_id: str,
                          eval_result: dict) -> dict:
        return {
            "type": "FALLBACK",
            "action": "reroute_to_simpler_model",
            "reason": f"Quality score: {eval_result['overall_score']}",
        }

    def _pass_through(self, session_id: str,
                      eval_result: dict) -> dict:
        return {"type": "PASS", "action": "none"}
</code></pre>

<h2 id="section-6-opentelemetry-telemetry-data-plane-vs-evaluation-control-plane" tabindex="-1">6. OpenTelemetry: Telemetry Data Plane vs Evaluation Control Plane<a href="#section-6-opentelemetry-telemetry-data-plane-vs-evaluation-control-plane" class="heading-anchor" aria-label="6. OpenTelemetry: Telemetry Data Plane vs Evaluation Control Plane 항목 링크">#</a></h2>
<p>Fiddler AI의 최근 분석은 이 아키텍처의 핵심 구분을 명확히 합니다:</p>
<blockquote>
<p><strong>OpenTelemetry is the data plane. It captures what happened. Evaluation is the control plane. It assesses whether what happened was acceptable.</strong></p>
</blockquote>
<p>이 구분은 다음과 같은 구조적 의미를 가집니다:</p>
<pre><code>┌──────────────────────────────────────────────┐
│            Control Plane                     │
│  (Evaluation, Scoring, Enforcement, Policy)  │
├──────────────────────────────────────────────┤
│            Data Plane                        │
│  (OpenTelemetry: Trace, Metric, Log)        │
├──────────────────────────────────────────────┤
│            Agent Runtime                     │
│  (MCP Tools, A2A Protocol, LLM Calls)       │
└──────────────────────────────────────────────┘
</code></pre>
<p>OpenTelemetry가 데이터 플레인으로 정착하면서, 평가와 제어 플레인은 그 위에 구축되는 별도의 계층이 되었습니다. 이 계층 분리는 엔터프라이즈 배포에서 중요한 의미를 가집니다:</p>
<ul>
<li><strong>데이터 플레인은 변경에 강함</strong>: 인스트루먼테이션은 한 번 구축하면 LLM 변경에도 영향을 받지 않음</li>
<li><strong>컨트롤 플레인은 빠르게 진화</strong>: 평가 기준은 비즈니스 요구사항에 따라 지속적으로 업데이트 가능</li>
<li><strong>정책 적용은 분리 가능</strong>: 규정 준수 정책을 데이터 수집과 독립적으로 변경할 수 있음</li>
</ul>
<hr>
<h2 id="section-7-비즈니스-플레인-observability에서-roi로" tabindex="-1">7. 비즈니스 플레인: Observability에서 ROI로<a href="#section-7-%EB%B9%84%EC%A6%88%EB%8B%88%EC%8A%A4-%ED%94%8C%EB%A0%88%EC%9D%B8-observability%EC%97%90%EC%84%9C-roi%EB%A1%9C" class="heading-anchor" aria-label="7. 비즈니스 플레인: Observability에서 ROI로 항목 링크">#</a></h2>
<p>마지막이자 가장 중요한 계층입니다. 에이전트 옵저버빌리티의 궁극적인 목표는 **"에이전트를 더 잘 운영하는 것"**이 아니라 **"에이전트의 비즈니스 가치를 증명하고 극대화하는 것"**입니다.</p>
<p>Microsoft Foundry의 Build 2026 발표에는 중요한 ROI 대시보드가 포함되었습니다. CFO가 물어볼 세 가지 질문에 답해야 합니다:</p>
<ol>
<li>
<p><strong>이 에이전트가 우리에게 얼마를 절약해 주고 있나요?</strong></p>
<ul>
<li>비용 측정: LLM 호출당 토큰 비용 + 평가 인프라 비용 (Evaluation Trust Tax)</li>
<li>절감 측정: 수동 처리 대비 시간 절감 × 인건비</li>
</ul>
</li>
<li>
<p><strong>에이전트가 작업을 얼마나 잘 수행하고 있나요?</strong></p>
<ul>
<li>Task Success Rate (TSR): 에이전트가 의도된 작업을 완료한 비율</li>
<li>Human Intervention Rate (HIR): 사람이 개입해야 했던 비율 (낮을수록 좋음)</li>
</ul>
</li>
<li>
<p><strong>이 에이전트가 시간이 지남에 따라 개선되고 있나요?</strong></p>
<ul>
<li>TSR 트렌드 (주간/월간)</li>
<li>에이전트 개선 루프 (traces → dataset → retrain → redeploy)의 완료율</li>
</ul>
</li>
</ol>
<h3 id="section-roi-계산-예시" tabindex="-1">ROI 계산 예시<a href="#section-roi-%EA%B3%84%EC%82%B0-%EC%98%88%EC%8B%9C" class="heading-anchor" aria-label="ROI 계산 예시 항목 링크">#</a></h3>
<pre><code>가상의 사례: 엔터프라이즈 IT 헬프데스크 에이전트

월간 비용:
  - LLM API 호출 비용: $3,200
  - OTel 인프라: $400
  - 평가 파이프라인: $600
  - 총 운영 비용: $4,200

월간 절감:
  - 대체된 Tier-1 인시던트: 1,200건 × $25/건 = $30,000
  - 해결 시간 단축: 평균 45분 → 12분 = 73% 단축
  - 총 절감: $30,000

월간 ROI: ($30,000 - $4,200) / $4,200 = 614%
</code></pre>
<p>이러한 ROI 계산은 옵저버빌리티 인프라 없이는 불가능합니다. 측정할 수 없으면 증명할 수 없고, 증명할 수 없으면 투자를 받을 수 없습니다.</p>
<hr>
<h2 id="section-8-결론-2026년-agent-observability의-5가지-진실" tabindex="-1">8. 결론: 2026년 Agent Observability의 5가지 진실<a href="#section-8-%EA%B2%B0%EB%A1%A0-2026%EB%85%84-agent-observability%EC%9D%98-5%EA%B0%80%EC%A7%80-%EC%A7%84%EC%8B%A4" class="heading-anchor" aria-label="8. 결론: 2026년 Agent Observability의 5가지 진실 항목 링크">#</a></h2>
<p>AI Agent Observability는 선택이 아닌 필수 인프라가 되었습니다. Microsoft Build 2026의 발표와 Coralogix의 2억 달러 투자는 이 시장의 성숙도를 증명합니다.</p>
<p><strong>이 글이 말해주는 5가지 핵심 진실:</strong></p>
<ol>
<li>
<p><strong>APM만으로는 충분하지 않다</strong>: 결정론적 소프트웨어를 위해 설계된 기존 관측성 스택은 비결정론적 에이전트의 의사결정 품질을 측정할 수 없습니다.</p>
</li>
<li>
<p><strong>OpenTelemetry는 시작일 뿐이다</strong>: OTel은 데이터 플레인(무슨 일이 일어났는가)을 해결하지만, 컨트롤 플레인(그것이 괜찮은가)은 평가와 정책 계층이 필요합니다.</p>
</li>
<li>
<p><strong>Multi-turn 평가가 복합 실패를 잡는다</strong>: 단일 턴 평가는 컨텍스트 드리프트, 골 드리프트, 모순, 안전 회귀를 놓칩니다.</p>
</li>
<li>
<p><strong>샘플링 전략이 비용과 신뢰도의 균형을 결정한다</strong>: Intelligent Trace Sampling 없이는 모든 트레이스를 평가하는 비용이 감당할 수 없습니다.</p>
</li>
<li>
<p><strong>옵저버빌리티는 ROI의 전제 조건이다</strong>: 측정할 수 없으면 개선할 수 없고, 개선할 수 없으면 투자를 받을 수 없습니다.</p>
</li>
</ol>
<p>이 글이 다루는 내용은 에이전트의 수명주기(Lifecycle) 전체를 포괄합니다. MCP가 툴 연결을, A2A가 에이전트 간 통신을 표준화했다면, 이제 Observability는 그 위에서 실행되는 모든 에이전트의 신뢰성과 비즈니스 가치를 보장하는 마지막 퍼즐 조각입니다.</p>
