17:T724b,<h2 id="section-1-들어가며-취소는-예외가-아니라-아키텍처다" tabindex="-1">1. 들어가며: 취소는 예외가 아니라 아키텍처다<a href="#section-1-%EB%93%A4%EC%96%B4%EA%B0%80%EB%A9%B0-%EC%B7%A8%EC%86%8C%EB%8A%94-%EC%98%88%EC%99%B8%EA%B0%80-%EC%95%84%EB%8B%88%EB%9D%BC-%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98%EB%8B%A4" class="heading-anchor" aria-label="1. 들어가며: 취소는 예외가 아니라 아키텍처다 항목 링크">#</a></h2>
<p>웹 애플리케이션에서 사용자가 검색어를 입력할 때마다 API 요청이 발생한다. 사용자가 다음 글자를 입력하는 순간, 이전 요청은 더 이상 필요하지 않다. 이때 우리는 무엇을 하는가?</p>
<p>대부분의 코드는 이렇게 되어 있다:</p>
<pre><code class="language-typescript">// ❌ 취소를 무시하는 패턴 — 가장 흔하지만 가장 위험하다
let lastAbortController: AbortController | null = null;

function search(query: string) {
  lastAbortController?.abort(); // 이전 요청 취소
  lastAbortController = new AbortController();
  
  fetch(`/api/search?q=${query}`, {
    signal: lastAbortController.signal,
  });
}
</code></pre>
<p>이 코드는 동작한다. 하지만 이것은 <strong>취소를 '도구'로만 사용</strong>한 예시다. 취소를 **'아키텍처 패턴'**으로 승격시키면, 단순한 fetch 중단을 넘어서:</p>
<ul>
<li>분산 시스템 전체의 Graceful Shutdown</li>
<li>Agent Task의 우아한 중단</li>
<li>리소스 누수 없는 비동기 작업 관리</li>
<li>에러 핸들링과 취소의 명확한 분리</li>
</ul>
<p>를 실현할 수 있다.</p>
<p>이 글에서는 JavaScript AbortController의 내부 동작 원리부터 시작해서, Signal Propagation 패턴, CancellationToken 체인, 그리고 최종적으로 분산 Agent 시스템에서의 취소 아키텍처까지를 TypeScript 코드와 함께 단계적으로 탐구한다.</p>

<h2 id="section-2-abortcontroller의-내부-동작-원리-eventemitter의-정교한-변주" tabindex="-1">2. AbortController의 내부 동작 원리: EventEmitter의 정교한 변주<a href="#section-2-abortcontroller%EC%9D%98-%EB%82%B4%EB%B6%80-%EB%8F%99%EC%9E%91-%EC%9B%90%EB%A6%AC-eventemitter%EC%9D%98-%EC%A0%95%EA%B5%90%ED%95%9C-%EB%B3%80%EC%A3%BC" class="heading-anchor" aria-label="2. AbortController의 내부 동작 원리: EventEmitter의 정교한 변주 항목 링크">#</a></h2>
<h3 id="section-2-1-구조-분석" tabindex="-1">2.1 구조 분석<a href="#section-2-1-%EA%B5%AC%EC%A1%B0-%EB%B6%84%EC%84%9D" class="heading-anchor" aria-label="2.1 구조 분석 항목 링크">#</a></h3>
<p>AbortController는 겉보기에는 단순해 보이지만, 내부적으로는 <strong>Observer Pattern + 상태 머신</strong>의 조합이다:</p>
<pre><code class="language-typescript">// AbortController의 내부 구조 (개념적)
class InternalAbortController {
  private _signal: InternalAbortSignal;
  private _aborted = false;

  constructor() {
    this._signal = new InternalAbortSignal(this);
  }

  abort(reason?: unknown) {
    if (this._aborted) return; // idempotent: 한 번 abort되면 재호출 무시
    this._aborted = true;
    this._signal._fireAbort(reason ?? new DOMException('The operation was aborted'));
  }

  get signal() { return this._signal; }
}

class InternalAbortSignal {
  private _onabort: ((ev: Event) => void) | null = null;
  private _listeners = new Set&#x3C;() => void>();
  private _aborted = false;
  private _reason: unknown;

  constructor(private _controller: InternalAbortController) {}

  get aborted() { return this._aborted; }
  get reason() { return this._reason; }

  // abort 이벤트 리스너 등록 — 사실상 EventEmitter
  addEventListener(type: 'abort', listener: () => void) {
    if (this._aborted) {
      // 이미 중단된 Signal에 리스너를 등록하면 즉시 실행
      queueMicrotask(listener);
      return;
    }
    this._listeners.add(listener);
  }

  removeEventListener(type: 'abort', listener: () => void) {
    this._listeners.delete(listener);
  }

  _fireAbort(reason: unknown) {
    this._aborted = true;
    this._reason = reason;
    // 이미 중단 상태로 리스너들을 실행
    for (const listener of this._listeners) {
      try { listener(); } catch { /* 개별 리스너 실패가 전체를 죽이지 않음 */ }
    }
    this._onabort?.({ type: 'abort' } as Event);
    this._listeners.clear(); // 메모리 누수 방지
  }
}
</code></pre>
<p>핵심 설계 결정 세 가지:</p>
<ol>
<li>
<p><strong>Idempotent Abort</strong>: <code>abort()</code>는 한 번만 유효하다. 두 번째 호출은 무시된다. 이는 Signal을 구독하는 모든 소비자가 <code>aborted</code> 상태를 확인할 수 있는 안전한 단일 진실 공급원(Single Source of Truth)을 보장한다.</p>
</li>
<li>
<p><strong>지연 리스너 등록 (Late Subscriber Handling)</strong>: 이미 중단된 Signal에 리스너를 등록하면, 리스너가 <code>queueMicrotask</code>를 통해 <strong>즉시 비동기적으로 실행</strong>된다. 이는 <code>await</code> 이후에 Signal을 확인하는 late subscriber도 누락 없이 취소 이벤트를 수신할 수 있게 한다.</p>
</li>
<li>

</li>

<h2 id="section-3-signal-propagation-체인-레이스-그리고-타임아웃" tabindex="-1">3. Signal Propagation: 체인, 레이스, 그리고 타임아웃<a href="#section-3-signal-propagation-%EC%B2%B4%EC%9D%B8-%EB%A0%88%EC%9D%B4%EC%8A%A4-%EA%B7%B8%EB%A6%AC%EA%B3%A0-%ED%83%80%EC%9E%84%EC%95%84%EC%9B%83" class="heading-anchor" aria-label="3. <h3 id="section-3-1-signal-chaining-부모-자식-취소-전파" tabindex="-1">3.1 Signal Chaining (부모-자식 취소 전파)<a href="#section-3-1-signal-chaining-%EB%B6%80%EB%AA%A8-%EC%9E%90%EC%8B%9D-%EC%B7%A8%EC%86%8C-%EC%A0%84%ED%8C%8C" class="heading-anchor" aria-label="3.1 Signal Chaining (부모-자식 취소 전파) 항목 링크">#</a></h3>
<p>실제 애플리케이션에서는 단일 취소가 아니라 <strong>계층적 취소</strong>가 필요하다. 예를 들어, 페이지를 떠날 때 모든 활성 요청을 취소하고, 각 요청 내에서도 여러 단계의 하위 작업이 있다면:</p>
<pre><code class="language-typescript">// Signal Chaining — 부모가 취소되면 모든 자식도 취소된다
function createChildSignal(parent: AbortSignal, timeoutMs?: number): AbortController {
  const child = new AbortController();
  
  // 부모가 취소되면 자식도 취소
  const onParentAbort = () => {
    child.abort(parent.reason); // 부모의 이유를 그대로 전파
  };
  
  // 이미 부모가 취소된 경우
  if (parent.aborted) {
    child.abort(parent.reason);
    return child;
  }
  
  parent.addEventListener('abort', onParentAbort, { once: true });
  
  // 타임아웃: 지정된 시간이 지나면 자동 취소
  if (timeoutMs !== undefined) {
    const timeoutId = setTimeout(() => {
      child.abort(new DOMException('Operation timed out', 'TimeoutError'));
    }, timeoutMs);
    
    // 자식이 먼저 취소되면 타임아웃 정리
    child.signal.addEventListener('abort', () => clearTimeout(timeoutId), { once: true });
  }
  
  return child;
}
</code></pre>
<h3 id="section-3-2-signal-racing-여러-취소-소스-중-먼저-도착하는-것-사용" tabindex="-1">3.2 Signal Racing: 여러 취소 소스 중 먼저 도착하는 것 사용<a href="#section-3-2-signal-racing-%EC%97%AC%EB%9F%AC-%EC%B7%A8%EC%86%8C-%EC%86%8C%EC%8A%A4-%EC%A4%91-%EB%A8%BC%EC%A0%80-%EB%8F%84%EC%B0%A9%ED%95%98%EB%8A%94-%EA%B2%83-%EC%82%AC%EC%9A%A9" class="heading-anchor" aria-label="3.2 Signal Racing: 여러 취소 소스 중 먼저 도착하는 것 사용 항목 링크">#</a></h3>
<p>때로는 하나의 작업이 여러 취소 조건을 가질 수 있다. 페이지 이탈 <strong>또는</strong> 사용자 명시적 취소 <strong>또는</strong> 5초 타임아웃 중 먼저 발생하는 것으로 취소해야 한다면:</p>
<pre><code class="language-typescript">// Signal Racing — 여러 취소 소스 중 가장 빠른 것을 사용
function raceSignals(signals: AbortSignal[]): AbortController {
  const controller = new AbortController();
  
  for (const signal of signals) {
    if (signal.aborted) {
      controller.abort(signal.reason);
      return controller;
    }
    
    signal.addEventListener('abort', () => {
      controller.abort(signal.reason);
    }, { once: true });
  }
  
  return controller;
}

// 사용 예
function fetchWithMultipleCancellation(url: string) {
  const pageLeaveSignal = getPageLeaveSignal();   // 페이지 이탈
  const userCancelSignal = getUserCancelSignal();   // 사용자 취소 버튼
  const timeoutSignal = AbortSignal.timeout(5000);  // 5초 타임아웃
  
  const raceController = raceSignals([
    pageLeaveSignal,
    userCancelSignal,
    timeoutSignal,
  ]);
  
  return fetch(url, { signal: raceController.signal });
}
</code></pre>
<h3 id="section-3-3-abortsignal-timeout-가장-우아한-타임아웃-패턴" tabindex="-1">3.3 AbortSignal.timeout() — 가장 우아한 타임아웃 패턴<a href="#section-3-3-abortsignal-timeout-%EA%B0%80%EC%9E%A5-%EC%9A%B0%EC%95%84%ED%95%9C-%ED%83%80%EC%9E%84%EC%95%84%EC%9B%83-%ED%8C%A8%ED%84%B4" class="heading-anchor" aria-label="3.3 AbortSignal.timeout() — 가장 우아한 타임아웃 패턴 항목 링크">#</a></h3>
<p>2024년에 추가된 <code>AbortSignal.timeout()</code>은 기존의 <code>setTimeout</code> + <code>clearTimeout</code> 패턴을 완전히 대체한다:</p>
<pre><code class="language-typescript">// 🚫 OLD: 수동 타임아웃 관리

  const controller = new AbortController();
  const timeoutId = setTimeout(() => controller.abort(), 5000);
  
  return fetch(url, { signal: controller.signal })
    .finally(() => clearTimeout(timeoutId)); // 누락되기 쉬운 정리

// ✅ NEW: AbortSignal.timeout()
function newWay(url: string) {
  return fetch(url, { signal: AbortSignal.timeout(5000) });
  // timeout이 만료되면 TimeoutError와 함께 자동 취소
}
</code></pre>
<p><code>AbortSignal.timeout()</code>의 숨은 장점은 <strong>취소 이유의 타입 안전성</strong>에 있다:</p>
<pre><code class="language-typescript">try {

  } else {
    // 네트워크 오류 등

  }
}
</code></pre>

<h2 id="section-4-abortsignal-cancellationtoken-추상화-레이어-설계" tabindex="-1">4. AbortSignal → CancellationToken: 추상화 레이어 설계<a href="#section-4-abortsignal-cancellationtoken-%EC%B6%94%EC%83%81%ED%99%94-%EB%A0%88%EC%9D%B4%EC%96%B4-%EC%84%A4%EA%B3%84" class="heading-anchor" aria-label="4. AbortSignal → CancellationToken: 추상화 레이어 설계 항목 링크">#</a></h2>
<p>브라우저가 아닌 환경(Node.js, Worker, Edge Runtime)에서도 일관된 취소 메커니즘이 필요하다. 이를 위해 AbortSignal을 더 일반적인 <strong>CancellationToken</strong>으로 추상화할 수 있다:</p>
<pre><code class="language-typescript">// CancellationToken — 환경 독립적인 취소 인터페이스
interface CancellationToken {
  readonly isCancellationRequested: boolean;
  readonly reason?: unknown;
  onCancelled(callback: () => void): () => void; // unsubscribe 함수 반환
  throwIfCancelled(): void;
}

// 브라우저 AbortSignal → CancellationToken 어댑터
class AbortSignalToken implements CancellationToken {
  constructor(private signal: AbortSignal) {}
  
  get isCancellationRequested() { return this.signal.aborted; }
  get reason() { return this.signal.reason; }
  
  onCancelled(callback: () => void): () => void {
    if (this.signal.aborted) {
      queueMicrotask(callback);
      return () => {}; // 이미 취소됨, unsubscribe 불필요
    }
    
    const handler = () => callback();
    this.signal.addEventListener('abort', handler, { once: true });
    return () => this.signal.removeEventListener('abort', handler);
  }
  
  throwIfCancelled() {
    if (this.signal.aborted) {
      throw this.signal.reason instanceof Error
        ? this.signal.reason
        : new DOMException(String(this.signal.reason), 'AbortError');
    }
  }
}

// 사용 예: CancellationToken을 받는 제네릭 함수
async function withCancellation&#x3C;T>(
  fn: (token: CancellationToken) => Promise&#x3C;T>,
  signal?: AbortSignal,
  timeoutMs?: number
): Promise&#x3C;T> {
  const effectiveSignal = timeoutMs !== undefined
    ? AbortSignal.any([signal ?? new AbortController().signal, AbortSignal.timeout(timeoutMs)])
    : signal ?? new AbortController().signal;
  
  const token = new AbortSignalToken(effectiveSignal);
  return fn(token);
}
</code></pre>
<p>이 추상화의 가치는:</p>
<ol>
<li><strong>테스트 용이성</strong>: 모의 CancellationToken을 주입하여 취소 시나리오를 쉽게 테스트</li>
<li><strong>환경 독립성</strong>: 브라우저/Node.js/Worker에서 동일한 인터페이스 사용</li>
<li><strong>타임아웃 + 취소의 조합</strong>: 복합 취소 조건을 단일 토큰으로 통합</li>
</ol>

<h2 id="section-5-분산-시스템에서의-cancellation-설계-패턴" tabindex="-1">5. 분산 시스템에서의 Cancellation 설계 패턴<a href="#section-5-%EB%B6%84%EC%82%B0-%EC%8B%9C%EC%8A%A4%ED%85%9C%EC%97%90%EC%84%9C%EC%9D%98-cancellation-%EC%84%A4%EA%B3%84-%ED%8C%A8%ED%84%B4" class="heading-anchor" aria-label="5. 분산 시스템에서의 Cancellation 설계 패턴 항목 링크">#</a></h2>
<h3 id="section-5-1-문제-취소는-전파되어야-한다" tabindex="-1">5.1 문제: 취소는 전파되어야 한다<a href="#section-5-1-%EB%AC%B8%EC%A0%9C-%EC%B7%A8%EC%86%8C%EB%8A%94-%EC%A0%84%ED%8C%8C%EB%90%98%EC%96%B4%EC%95%BC-%ED%95%9C%EB%8B%A4" class="heading-anchor" aria-label="5.1 문제: 취소는 전파되어야 한다 항목 링크">#</a></h3>
<p>마이크로서비스나 AI Agent 시스템에서 하나의 요청은 여러 서비스에 걸쳐 있다. 사용자가 A 서비스에 요청을 보내고, A는 B와 C를 호출하고, B는 다시 D를 호출한다. 이때 사용자가 요청을 취소하면 A, B, C, D 모두에게 취소가 전파되어야 한다.</p>
<p>이것이 <strong>Cancellation Propagation</strong> 문제다:</p>
<pre><code>사용자 ──▶ A 서비스 ──▶ B 서비스 ──▶ D 서비스
               ├──▶ C 서비스
</code></pre>
<p>B나 C가 여전히 실행 중이라면 자원이 낭비된다. 더 나쁜 경우, D가 데이터베이스 락을 획득한 상태라면 데드락까지 발생할 수 있다.</p>
<h3 id="section-5-2-typescript-구현-계층적-cancellationtoken-전파" tabindex="-1">5.2 TypeScript 구현: 계층적 CancellationToken 전파<a href="#section-5-2-typescript-%EA%B5%AC%ED%98%84-%EA%B3%84%EC%B8%B5%EC%A0%81-cancellationtoken-%EC%A0%84%ED%8C%8C" class="heading-anchor" aria-label="5.2 TypeScript 구현: 계층적 CancellationToken 전파 항목 링크">#</a></h3>
<pre><code class="language-typescript">// HTTP 요청에 CancellationToken을 전달하는 미들웨어
interface CancellableRequest {
  signal: AbortSignal;
  // ... 다른 요청 속성
}

// API Gateway에서 취소 전파
async function apiGatewayHandler(req: CancellableRequest) {
  const taskId = crypto.randomUUID();
  
  // 부모 컨트롤러: 클라이언트 연결이 끊기면 취소
  const parentController = new AbortController();
  req.signal.addEventListener('abort', () => {
    parentController.abort(new DOMException('Client disconnected', 'AbortError'));
  }, { once: true });
  
  // A → B, A → C: 각각 자식 Signal 생성
  const [resultB, resultC] = await Promise.all([
    serviceB.call({ ...req, signal: createChildSignal(parentController.signal, 10000).signal }),
    serviceC.call({ ...req, signal: createChildSignal(parentController.signal, 10000).signal }),
  ]);
  
  return { resultB, resultC };
}

// Service B가 다시 Service D를 호출
class ServiceB {
  async call(req: CancellableRequest): Promise&#x3C;Result> {
    const childController = createChildSignal(req.signal, 5000);
    
    // 여러 하위 작업을 취소 가능하게 실행
    try {
      const [dbResult, dResult] = await Promise.all([
        this.queryDatabase(childController.signal),
        serviceD.call({ signal: createChildSignal(childController.signal).signal }),
      ]);
      
      return { dbResult, dResult };
    } catch (err) {
      if (err instanceof DOMException &#x26;&#x26; err.name === 'AbortError') {
        // 취소 시 정리 작업 수행
        await this.rollbackPartialWork();
      }
      throw err;
    }
  }
}
</code></pre>
<h3 id="section-5-3-ai-agent-시스템에서의-task-cancellation" tabindex="-1">5.3 AI Agent 시스템에서의 Task Cancellation<a href="#section-5-3-ai-agent-%EC%8B%9C%EC%8A%A4%ED%85%9C%EC%97%90%EC%84%9C%EC%9D%98-task-cancellation" class="heading-anchor" aria-label="5.3 AI Agent 시스템에서의 Task Cancellation 항목 링크">#</a></h3>
<p>AI Agent 환경에서는 취소가 더 복잡하다 — LLM 호출, 툴 실행, 상태 업데이트가 동시에 일어나기 때문:</p>
<pre><code class="language-typescript">// Agent Task 실행기 — 취소 가능한 Agent 실행
class AgentTaskRunner {
  async executeTask(
    task: AgentTask,
    token: CancellationToken
  ): Promise&#x3C;AgentResult> {
    // 1단계: 계획 수립 (취소 가능)
    token.throwIfCancelled();
    const plan = await this.plan(task, token);
    
    // 2단계: 단계별 실행 (각 단계에서 취소 확인)
    const results: StepResult[] = [];
    for (const step of plan.steps) {
      token.throwIfCancelled(); // 매 단계마다 취소 확인
      
      // 타임아웃이 있는 상태에서 LLM 호출
      const llmToken = new AbortSignalToken(
        AbortSignal.timeout(30000) // 각 LLM 호출은 30초 제한
      );
      
      const stepResult = await this.executeStep(step, {
        ...llmToken,
        parentToken: token,
      });
      
      results.push(stepResult);
    }
    
    return this.synthesize(task, results);
  }
  
  private async executeStep(
    step: Step,
    context: { parentToken: CancellationToken }
  ): Promise&#x3C;StepResult> {
    // LLM 추론 + 툴 호출을 동시 실행
    const [llmResponse, toolResults] = await Promise.all([
      this.callLLM(step.prompt, context.parentToken),
      this.callTools(step.tools, context.parentToken),
    ]);
    
    return { llmResponse, toolResults };
  }
}
</code></pre>
<h3 id="section-5-4-cache-stampede-방어와-조기-취소" tabindex="-1">5.4 Cache Stampede 방어와 조기 취소<a href="#section-5-4-cache-stampede-%EB%B0%A9%EC%96%B4%EC%99%80-%EC%A1%B0%EA%B8%B0-%EC%B7%A8%EC%86%8C" class="heading-anchor" aria-label="5.4 Cache Stampede 방어와 조기 취소 항목 링크">#</a></h3>
<p>오늘의 System Design Knowledge Pill 주제인 <strong>Cache Stampede</strong>도 취소 메커니즘과 밀접한 관련이 있다:</p>
<pre><code class="language-typescript">// Cache Stampede 방어 + Signal 기반 조기 완료
class CacheStampedeDefender&#x3C;T> {
  private inflight = new Map&#x3C;string, {
    promise: Promise&#x3C;T>;
    controller: AbortController;
  }>();
  
  async get(key: string, fetch: (signal: AbortSignal) => Promise&#x3C;T>): Promise&#x3C;T> {
    // 이미 진행 중인 요청이 있다면 — Signal을 공유
    const existing = this.inflight.get(key);
    if (existing) return existing.promise;
    
    const controller = new AbortController();
    
    const promise = fetch(controller.signal).finally(() => {
      this.inflight.delete(key);
    });
    
    this.inflight.set(key, { promise, controller });
    
    // 경합: 첫 번째 완료자가 나머지 취소
    const result = await promise;
    
    // 같은 키로 대기 중인 다른 요청들은 자동 취소
    // (Signal을 공유하지 않고 각자 fetch했다면 중복 요청이 발생했을 것)
    
    return result;
  }
}
</code></pre>

<h2 id="section-6-고급-패턴-abortsignal-any-와-복합-취소" tabindex="-1">6. 고급 패턴: AbortSignal.any()와 복합 취소<a href="#section-6-%EA%B3%A0%EA%B8%89-%ED%8C%A8%ED%84%B4-abortsignal-any-%EC%99%80-%EB%B3%B5%ED%95%A9-%EC%B7%A8%EC%86%8C" class="heading-anchor" aria-label="6. 고급 패턴: AbortSignal.any()와 복합 취소 항목 링크">#</a></h2>
<p>2025년 표준에 포함된 <code>AbortSignal.any()</code>는 여러 Signal 중 <strong>하나라도</strong> 취소되면 함께 취소되는 복합 Signal을 생성한다:</p>
<pre><code class="language-typescript">// AbortSignal.any() — N 중 1 취소 = 전체 취소
function fetchWithMultipleGuards(url: string) {
  const pageVisibility = new AbortController();
  
  // 페이지가 숨겨지면 취소
  document.addEventListener('visibilitychange', () => {
    if (document.hidden) {
      pageVisibility.abort(new DOMException('Page hidden', 'AbortError'));
    }
  }, { signal: pageVisibility.signal }); // ★ 리스너 자기 자신도 취소 가능
  
  const combined = AbortSignal.any([
    AbortSignal.timeout(8000),      // 8초 타임아웃
    pageVisibility.signal,           // 페이지 숨김
    userAbortController.signal,      // 사용자 명시적 취소
  ]);
  
  return fetch(url, { signal: combined });
}
</code></pre>
<h3 id="section-abortsignal-any-vs-racesignals" tabindex="-1">AbortSignal.any() vs RaceSignals()<a href="#section-abortsignal-any-vs-racesignals" class="heading-anchor" aria-label="AbortSignal.any() vs RaceSignals() 항목 링크">#</a></h3>
<p>둘의 차이는 <strong>취소 이유 전파</strong>에 있다:</p>
<pre><code class="language-typescript">// AbortSignal.any() — 첫 번째 취소 이유를 사용
const combined = AbortSignal.any([sig1, sig2]);
// combined.reason === 먼저 취소된 Signal의 reason

// 수동 RaceSignals — 취소 이유를 명시적으로 전파
function raceSignals(signals: AbortSignal[]) {
  const controller = new AbortController();
  for (const sig of signals) {
    sig.addEventListener('abort', () => {
      controller.abort(sig.reason); // 명시적 이유 전파
    }, { once: true });
  }
  return controller;
}
</code></pre>
<p>실무에서는 <code>AbortSignal.any()</code>가 더 간결하고 표준에 가깝지만, 취소 이유에 따른 분기 처리가 필요하다면 수동 구현이 유리하다.</p>

<h2 id="section-7-실전-응용-react-query-취소-통합" tabindex="-1">7. 실전 응용: React Query + 취소 통합<a href="#section-7-%EC%8B%A4%EC%A0%84-%EC%9D%91%EC%9A%A9-react-query-%EC%B7%A8%EC%86%8C-%ED%86%B5%ED%95%A9" class="heading-anchor" aria-label="7. 실전 응용: React Query + 취소 통합 항목 링크">#</a></h2>
<p>React Query의 <code>queryFn</code>은 이미 <code>AbortSignal</code>을 인자로 받는다. 하지만 대부분의 코드는 이를 무시한다:</p>
<pre><code class="language-typescript">// ❌ React Query에서 Signal 무시
const { data } = useQuery({
  queryKey: ['search', query],
  queryFn: () => fetchSearch(query), // 취소 불가능
});

// ✅ React Query에서 Signal 활용
const { data } = useQuery({
  queryKey: ['search', query],
  queryFn: ({ signal }) => fetchSearch(query, signal), // 취소 가능
});

async function fetchSearch(query: string, signal: AbortSignal): Promise&#x3C;Result[]> {
  // debounce + 취소: 이전 요청이 자연스럽게 취소됨
  await delay(300, signal); // AbortSignal을 지원하는 delay 함수
  const res = await fetch(`/api/search?q=${query}`, { signal });
  return res.json();
}

// AbortSignal을 지원하는 delay 유틸리티
function delay(ms: number, signal?: AbortSignal): Promise&#x3C;void> {
  return new Promise((resolve, reject) => {
    const timer = setTimeout(resolve, ms);
    signal?.addEventListener('abort', () => {
      clearTimeout(timer);
      reject(signal.reason);
    }, { once: true });
  });
}
</code></pre>
<p>이 패턴을 적용하면:</p>
<ul>
<li>검색어를 빠르게 입력할 때 이전 요청이 자동 취소</li>
<li>네트워크 요청과 디바운스 타이머가 모두 취소됨</li>
<li>불필요한 setState와 리렌더링 방지</li>
</ul>

<h2 id="section-9-결론-cancel-culture-in-engineering" tabindex="-1">9. 결론: Cancel Culture in Engineering<a href="#section-9-%EA%B2%B0%EB%A1%A0-cancel-culture-in-engineering" class="heading-anchor" aria-label="9. 결론: Cancel Culture in Engineering 항목 링크">#</a></h2>
<p>AbortController는 단순한 API가 아니다. 이것은 <strong>비동기 작업의 생명주기 관리</strong>에 대한 언어 수준의 선언이다. 자바의 <code>InterruptedException</code>이나 C#의 <code>CancellationToken</code>과 달리, JavaScript의 AbortSignal은:</p>
<ol>
<li><strong>Push 기반</strong>이다 — 소비자가 주기적으로 폴링하지 않아도 취소를 통지받는다.</li>
<li><strong>조합 가능(Composable)</strong> 하다 — <code>AbortSignal.any()</code>, <code>createChildSignal()</code>, <code>raceSignals()</code> 등으로 복합 취소 조건을 자연스럽게 표현할 수 있다.</li>
<li><strong>에러와 취소를 분리</strong>한다 — <code>AbortError</code>는 에러 핸들러가 아닌 취소 핸들러가 처리하며, 이는 시스템의 복원력을 높인다.</li>
</ol>
<p>분산 Agent 시스템이 보편화될수록, 취소 메커니즘은 단순한 UX 개선을 넘어 <strong>리소스 효율성과 시스템 안정성의 핵심 요소</strong>로 자리잡을 것이다. 오늘 다룬 AbortController의 설계 원칙 — Idempotency, Reason Propagation, Late Subscriber Safety — 은 단일 스레드 JavaScript를 넘어, 분산 시스템 전체에 적용될 수 있는 보편적인 취소 아키텍처의 기초를 제공한다.</p>
