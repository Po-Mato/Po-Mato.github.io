<h2 id="section-1-문제의-본질-왜-단순한-호출은-신뢰할-수-없는가" tabindex="-1">1. 문제의 본질: 왜 단순한 호출은 신뢰할 수 없는가<a href="#section-1-%EB%AC%B8%EC%A0%9C%EC%9D%98-%EB%B3%B8%EC%A7%88-%EC%99%9C-%EB%8B%A8%EC%88%9C%ED%95%9C-%ED%98%B8%EC%B6%9C%EC%9D%80-%EC%8B%A0%EB%A2%B0%ED%95%A0-%EC%88%98-%EC%97%86%EB%8A%94%EA%B0%80" class="heading-anchor" aria-label="1. 문제의 본질: 왜 단순한 호출은 신뢰할 수 없는가 항목 링크">#</a></h2>
<h3 id="section-1-1-이중-실패-문제-dual-write-problem" tabindex="-1">1.1 이중 실패 문제 (Dual Write Problem)<a href="#section-1-1-%EC%9D%B4%EC%A4%91-%EC%8B%A4%ED%8C%A8-%EB%AC%B8%EC%A0%9C-dual-write-problem" class="heading-anchor" aria-label="1.1 이중 실패 문제 (Dual Write Problem) 항목 링크">#</a></h3>
<p>가장 직관적인 구현은 이렇습니다:</p>
<pre><code class="language-python"># ⚠️ 이 코드는 신뢰할 수 없습니다

    order = db.orders.create(order_data)
    email_service.send(order.customer_email, "주문이 완료되었습니다")
    return order
</code></pre>
<p>이 코드에는 치명적인 문제가 있습니다. <code>db.orders.create()</code>는 성공했지만 <code>email_service.send()</code>가 실패하면 데이터베이스에는 주문이 있지만 이메일은 보내지 않습니다. 역으로, 이메일 전송 후 DB 트랜잭션이 롤백되면 이메지는 이미 발송된 상태입니다.</p>
<p>이것이 <strong>이중 실패(Dual Write)</strong> 문제입니다. 두 개의 서로 다른 시스템(데이터베이스와 메시지Broker)을 하나의 원자적 트랜잭션으로 묶을 수 없기 때문에, 어떤 작업은 성공하고 어떤 작업은 실패할 수 있습니다.</p>

<h2 id="section-3-transactional-outbox-패턴-정확한-구현" tabindex="-1">3. Transactional Outbox 패턴: 정확한 구현<a href="#section-3-transactional-outbox-%ED%8C%A8%ED%84%B4-%EC%A0%95%ED%99%95%ED%95%9C-%EA%B5%AC%ED%98%84" class="heading-anchor" aria-label="3. Transactional Outbox 패턴: 정확한 구현 항목 링크">#</a></h2>
<h3 id="section-3-1-핵심-아이디어" tabindex="-1">3.1 핵심 아이디어<a href="#section-3-1-%ED%95%B5%EC%8B%AC-%EC%95%84%EC%9D%B4%EB%94%94%EC%96%B4" class="heading-anchor" aria-label="3.1 핵심 아이디어 항목 링크">#</a></h3>
<p>핵심 통찰은 단순합니다: <strong>"메시지 발행도 하나의 트랜잭션으로 묶어라."</strong></p>
<p>Outbox 테이블은 애플리케이션의 DB 트랜잭션 내부에서 일반 테이블처럼 접근됩니다. 별도의 프로세스가 Outbox를 읽어 메시지Broker에 전달하고, 처리 완료된 레코드를 표시합니다.</p>
<pre><code class="language-python">def create_order(order_data: OrderData) -> Order:
    with db.transaction():
        order = db.orders.create(order_data)
        
        # ✨ Outbox에 INSERT — DB 트랜잭션의 일부
        db.outbox.create({
            "aggregate_type": "Order",
            "aggregate_id": order.id,
            "event_type": "OrderCreated",
            "payload": {
                "order_id": order.id,
                "customer_email": order.customer_email,
                "total_amount": str(order.total_amount),
                "created_at": order.created_at.isoformat()
            }
        })
        
        # 위 두 작업은同一个 트랜잭션으로 처리됩니다
        # → 둘 다 성공하거나 둘 다 롤백됩니다
    
    return order  # 이메일 전송은 여기서 완료되지 않음
</code></pre>
<p>주문 생성 함수에서 이메일 전송이 사라졌습니다. 이메일 전송은 Outbox 테이블에 레코드Insertion하는 것으로 대체되었습니다. 이것이 의미하는 바: <strong>주문이 성공하면 그에 대한 알림 Event도 반드시 Outbox에 존재합니다.</strong></p>
<h3 id="section-3-2-outbox-processor-relay-service" tabindex="-1">3.2 Outbox Processor (Relay Service)<a href="#section-3-2-outbox-processor-relay-service" class="heading-anchor" aria-label="3.2 Outbox Processor (Relay Service) 항목 링크">#</a></h3>
<p>별도의 프로세스가 Outbox 테이블을 읽고 메시지를 전달합니다:</p>
<pre><code class="language-python">class OutboxProcessor:
    def __init__(self, db: Database, broker: MessageBroker):
        self.db = db
        self.broker = broker
    
    def process_batch(self, batch_size: int = 100):
        with self.db.transaction():
            # 처리 대상 events를 선택 (FOR UPDATE로 행 잠금)
            events = self.db.query("""
                SELECT * FROM outbox 
                WHERE processed_at IS NULL 
                ORDER BY created_at 
                LIMIT %s
                FOR UPDATE SKIP LOCKED
            """, batch_size)
            
            if not events:
                return
            
            try:
                # Batch publish to message broker
                self.broker.publish_batch([
                    {"topic": f"domain.{e.event_type}", "message": e.payload}
                    for e in events
                ])
                
                # 처리 완료 표시
                event_ids = [e.id for e in events]
                self.db.execute("""
                    UPDATE outbox 
                    SET processed_at = NOW() 
                    WHERE id = ANY(%s)
                """, event_ids)
                
            except Exception as e:
                #失败了 — 다음 번 순회 때 다시 시도
                # 롤백되면 processed_at이 NULL로 남아있음
                logger.error(f"Batch publish failed: {e}")
                raise
</code></pre>
<p><strong>FOR UPDATE SKIP LOCKED</strong> 구문이 핵심입니다. 이것은 여러 Processor 인스턴스가 동시에 같은 레코드를 처리하지 않도록 보장합니다. OutboxProcessor를 여러Replica로 스케일링해도安全问题이 없습니다.</p>
<h3 id="section-3-3-중복-제거-멱등-consumer의-중요성" tabindex="-1">3.3 중복 제거: 멱등 consumer의 중요성<a href="#section-3-3-%EC%A4%91%EB%B3%B5-%EC%A0%9C%EA%B1%B0-%EB%A9%B1%EB%93%B1-consumer%EC%9D%98-%EC%A4%91%EC%9A%94%EC%84%B1" class="heading-anchor" aria-label="3.3 중복 제거: 멱등 consumer의 중요성 항목 링크">#</a></h3>
<p>At-least-once 환경에서 메시지 중복은不可避免합니다. Consumer는 멱등하게 동작해야 합니다:</p>
<pre><code class="language-python">class OrderEventHandler:
    def handle_order_created(self, message: dict):
        # 멱등성 보장: 이미 처리된 이벤트인지 확인
        event_id = message.get("event_id")
        if self.event_store.is_processed(event_id):
            logger.info(f"Event {event_id} already processed, skipping")
            return
        
        order_id = message["order_id"]
        if self.order_service.order_exists(order_id):
            logger.info(f"Order {order_id} already exists, skipping")
            return
        
        self.order_service.create_from_event(message)
        self.event_store.mark_processed(event_id)
</code></pre>
<p>Event ID를利用하여 멱등성을 확보하면, 메시지가 몇 번이고 중복 전달되어도 결과는 정확히 한 번의 효과와 동일합니다.</p>

<h2 id="section-5-순서-보장-같은-aggregate-내에서는-순서-보장" tabindex="-1">5. 순서 보장: 같은 Aggregate 내에서는 순서 보장<a href="#section-5-%EC%88%9C%EC%84%9C-%EB%B3%B4%EC%9E%A5-%EA%B0%99%EC%9D%80-aggregate-%EB%82%B4%EC%97%90%EC%84%9C%EB%8A%94-%EC%88%9C%EC%84%9C-%EB%B3%B4%EC%9E%A5" class="heading-anchor" aria-label="5. 순서 보장: 같은 Aggregate 내에서는 순서 보장 항목 링크">#</a></h2>
<h3 id="section-5-1-kafka-partitioning-전략" tabindex="-1">5.1 Kafka Partitioning 전략<a href="#section-5-1-kafka-partitioning-%EC%A0%84%EB%9E%B5" class="heading-anchor" aria-label="5.1 Kafka Partitioning 전략 항목 링크">#</a></h3>
<p>Outbox에서 발행된 이벤트가 같은 Aggregate(예: 같은 Order ID)에 대해서는 순서가 보장되어야 합니다. 이것은 Kafka에서 <strong>Partitioning 전략</strong>으로 해결합니다:</p>
<pre><code class="language-python">def publish_to_kafka(event: OutboxEvent):
    # 같은 aggregate_id는 항상 같은 partition으로
    partition = hash(event.aggregate_id) % num_partitions
    
    producer.send(
        topic=f"domain.{event.event_type}",
        value=event.payload,
        key=event.aggregate_id  # key 기반 partitioning
    )
</code></pre>
<p>Kafka에서 같은 Key를 가진 메시지는 항상 같은 Partition에 할당됩니다. Consumer 입장에서는 같은 Partition 내에서만 순서가 보장되므로, 같은 Aggregate ID를 Key로 사용하면 해당 Aggregate 내의 이벤트 순서가 보장됩니다.</p>
<h3 id="section-5-2partition-key-vs-message-key" tabindex="-1">5.2Partition Key vs Message Key<a href="#section-5-2partition-key-vs-message-key" class="heading-anchor" aria-label="5.2Partition Key vs Message Key 항목 링크">#</a></h3>
<p>실무에서 흔한 실수가 Partition Key를 event_type으로 설정하는 것입니다:</p>
<pre><code class="language-python"># ❌ 이 partition 전략은 순서를 보장하지 못합니다
producer.send(topic="domain.OrderEvents", key="OrderCreated")

# ✅ aggregate ID 기반 partition
producer.send(topic="domain.OrderEvents", key="ord-123")
</code></pre>
<p>event_type을 Key로 사용하면 같은 주문에 대한 <code>OrderCreated</code> → <code>OrderUpdated</code> → <code>OrderShipped</code> 이벤트가 다른 Partition에 갈 수 있고, Consumer에서 순서가 뒤섞일 수 있습니다.</p>

<h2 id="section-6-실무-체크리스트-outbox-패턴-구현-시-확인-사항" tabindex="-1">6. 실무 체크리스트: Outbox 패턴 구현 시 확인 사항<a href="#section-6-%EC%8B%A4%EB%AC%B4-%EC%B2%B4%ED%81%AC%EB%A6%AC%EC%8A%A4%ED%8A%B8-outbox-%ED%8C%A8%ED%84%B4-%EA%B5%AC%ED%98%84-%EC%8B%9C-%ED%99%95%EC%9D%B8-%EC%82%AC%ED%95%AD" class="heading-anchor" aria-label="6. 실무 체크리스트: Outbox 패턴 구현 시 확인 사항 항목 링크">#</a></h2>
<p>구현 전에 반드시 확인해야 할 실무적 항목들:</p>
<ul class="contains-task-list">
<li class="task-list-item"><input type="checkbox" disabled> <strong>Idempotent Consumer</strong>: Producer가 at-least-once를 보장하면, Consumer는 멱등해야 합니다</li>
<li class="task-list-item"><input type="checkbox" disabled> <strong>Outbox 테이블 인덱싱</strong>: <code>processed_at</code> 컬럼에 인덱스가 없으면Polling 시 전체 스캔 발생</li>
<li class="task-list-item"><input type="checkbox" disabled> <strong>배치 크기 설정</strong>: 너무 크면 메모리 부담, 너무 작으면 처리량 부족 (100-500 정도가 일반적)</li>
<li class="task-list-item"><input type="checkbox" disabled> <strong>실패 Retry 정책</strong>: Exponential backoff로 무한 재시도 방지</li>
<li class="task-list-item"><input type="checkbox" disabled> <strong>孤儿 이벤트 정리</strong>: 처리 완료된 Outbox 레코드는 따로 정리 정책 필요 (예: 7일 이상 경과 시 삭제)</li>
<li class="task-list-item"><input type="checkbox" disabled> <strong>모니터링</strong>: Outbox 테이블에 <code>processed_at IS NULL</code>인 레코드 수를 alerting하는 것이 중요</li>
</ul>

<h2 id="section-결론-이벤트-신뢰성은-아키텍처적-결정" tabindex="-1">결론: 이벤트 신뢰성은 아키텍처적 결정<a href="#section-%EA%B2%B0%EB%A1%A0-%EC%9D%B4%EB%B2%A4%ED%8A%B8-%EC%8B%A0%EB%A2%B0%EC%84%B1%EC%9D%80-%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98%EC%A0%81-%EA%B2%B0%EC%A0%95" class="heading-anchor" aria-label="결론: 이벤트 신뢰성은 아키텍처적 결정 항목 링크">#</a></h2>
<p>Transactional Outbox는 "그냥 메시지를 보내는" 코드 한 줄을 추가하는 것보다 훨씬 무겁습니다. 테이블, Processor, 중복 제거 로직, 모니터링까지 필요합니다.</p>
<p>그렇기에 Outbox 도입 전에 먼저自問해야 합니다: <strong>"이 메시지가 도착하지 않으면 어떤 일이 발생하는가?"</strong></p>
<p>만약 아무 일도 발생하지 않는다면(예: 비 kritische 알림), 단순한 at-least-once publish로 충분합니다. 하지만 재고 확인, 결제 처리, 예약 확정처럼 <strong>정확히 한 번</strong>이 필요한 영역이라면, Outbox 패턴의 복잡성은 반드시 감수해야 할 비용입니다.</p>
<p>분산 시스템에서 reliability는 항상 trade-off입니다. Outbox 패턴은 그 trade-off를 의식적으로 선택하는 아키텍처적 결정입니다.</p>20:["$","$L22",null,{"contentHtml":"$23"}]
