15:T489b,<h2 id="section-서론-에이전트가-하나가-아닌-이유" tabindex="-1">서론: 에이전트가 하나가 아닌 이유<a href="#section-%EC%84%9C%EB%A1%A0-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%EA%B0%80-%ED%95%98%EB%82%98%EA%B0%80-%EC%95%84%EB%8B%8C-%EC%9D%B4%EC%9C%A0" class="heading-anchor" aria-label="서론: 에이전트가 하나가 아닌 이유 항목 링크">#</a></h2>
<p>2024년도의 AI 에이전트는 단일 작업 Trojan Horse였다. "주문 처리" 하나를 위해 방대한 LLM에 모든 도구를 때려 넣었고, 그 결과 brittle하고 감시 불가능한 거대한 블랙박스가 탄생했다.</p>
<p>2026년 현재, 산업 전반에서 새로운 설계 패러다임이 자리 잡았다. <strong>단일 거대 에이전트 대신, 작은 특화 에이전트들이 메쉬(Mesh) 구조로 협업하는 Agent Mesh 아키텍처</strong>다. 이 글에서는 이 패러다임의 핵심 설계 원칙, Harness Engineering과의 관계, 그리고 실제 엔터프라이즈 구현 사례를 심층적으로 분석한다.</p>

<h2 id="section-1-왜-단일-에이전트가-실패하는가" tabindex="-1">1. 왜 단일 에이전트가 실패하는가<a href="#section-1-%EC%99%9C-%EB%8B%A8%EC%9D%BC-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%EA%B0%80-%EC%8B%A4%ED%8C%A8%ED%95%98%EB%8A%94%EA%B0%80" class="heading-anchor" aria-label="1. 왜 단일 에이전트가 실패하는가 항목 링크">#</a></h2>
<h3 id="section-1-1-책임의-분리-원칙과-에이전트-설계" tabindex="-1">1.1 책임의 분리 원칙과 에이전트 설계<a href="#section-1-1-%EC%B1%85%EC%9E%84%EC%9D%98-%EB%B6%84%EB%A6%AC-%EC%9B%90%EC%B9%99%EA%B3%BC-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8-%EC%84%A4%EA%B3%84" class="heading-anchor" aria-label="1.1 책임의 분리 원칙과 에이전트 설계 항목 링크">#</a></h3>
<p>마이크로서비스 아키텍처에서 각 서비스가 단일 책임을 가지듯이, AI 에이전트도 동일한 원칙이 필요하다. 하나의 거대 에이전트가 "고객 서비스 + 재무审计 + 재고 관리"를 모두 수행하려 한다면:</p>
<ul>
<li><strong>모델 크기 문제</strong>: 모든 도메인 지식을 하나의 컨텍스트에 담아야 하므로 프롬프트가 폭발적으로 증가한다.</li>
<li><strong>관심사 분리 실패</strong>: 고객 서비스 로직에 재무审计 규칙이 섞여 들어가며, 변경 시 사이드 이펙트 위험이 높아진다.</li>
<li><strong>장애 격리 불가</strong>: 하나의 도메인에서 오류가 발생하면 전체 에이전트가 영향을 받는다.</li>
</ul>
<h3 id="section-1-2-역할-기반-에이전트의-한계" tabindex="-1">1.2 역할 기반 에이전트의 한계<a href="#section-1-2-%EC%97%AD%ED%95%A0-%EA%B8%B0%EB%B0%98-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%EC%9D%98-%ED%95%9C%EA%B3%84" class="heading-anchor" aria-label="1.2 역할 기반 에이전트의 한계 항목 링크">#</a></h3>

<h3 id="section-2-1-에이전트-타입-분류" tabindex="-1">2.1 에이전트 타입 분류<a href="#section-2-1-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8-%ED%83%80%EC%9E%85-%EB%B6%84%EB%A5%98" class="heading-anchor" aria-label="2.1 에이전트 타입 분류 항목 링크">#</a></h3>

<h3 id="section-2-2-메쉬-통신-프로토콜-mcp-a2a" tabindex="-1">2.2 메쉬 통신 프로토콜 (MCP + A2A)<a href="#section-2-2-%EB%A9%94%EC%89%AC-%ED%86%B5%EC%8B%A0-%ED%94%84%EB%A1%9C%ED%86%A0%EC%BD%9C-mcp-a2a" class="heading-anchor" aria-label="2.2 메쉬 통신 프로토콜 (MCP + A2A) 항목 링크">#</a></h3>
<p>단일 에이전트 간의 통신에는 두 가지 프로토콜이 핵심적이다:</p>
<p><strong>MCP (Model Context Protocol)</strong>: 에이전트가 도구(Tools)를 호출할 때 사용. 단일 에이전트의 실행 단위다.</p>
<p><strong>A2A (Agent-to-Agent Protocol)</strong>: 에이전트가 다른 에이전트에게 태스크를 위임하거나 결과를 요청할 때 사용. 이는 2025년後半에 등장한 상대적으로 새로운 프로토콜로, HTTP+SSE 기반 event-driven 통신을 지원한다.</p>
<pre><code class="language-python"># A2A를 통한 에이전트 간 태스크 위임 예시
class ComplianceAgent:
    async def delegate_to_specialist(self, task: Task, specialist_id: str):
        # A2A 프로토콜로 스페셜리스트에게 위임
        message = A2AMessage(
            type="task_delegation",
            from_agent=self.agent_id,
            to_agent=specialist_id,
            payload={
                "task_type": task.type,
                "context": task.context,
                "callback_url": f"/mesh/{self.agent_id}/result"
            }
        )
        await self.mesh_channel.send(message)
    
    async def receive_result(self, result: TaskResult):
        # 비동기 결과를 수신하여 워크플로우 계속 진행
        await self.process_compliance_check(result)

<h3 id="section-2-3-harness-agent-mesh의-품질-게이트" tabindex="-1">2.3 Harness: Agent Mesh의 품질 게이트<a href="#section-2-3-harness-agent-mesh%EC%9D%98-%ED%92%88%EC%A7%88-%EA%B2%8C%EC%9D%B4%ED%8A%B8" class="heading-anchor" aria-label="2.3 Harness: Agent Mesh의 품질 게이트 항목 링크">#</a></h3>
<p>Harness Engineering은 Agent Mesh의 reliability를 좌우하는 핵심 요소다. Google의 Agent Development Kit (ADK) 2026 업데이트에서 강조된 바와 같이, harness setup만으로도 벤치마크 성능이 5% 이상 변동할 수 있다.</p>
<p>Harness는 크게 네 가지 레이어로 구성된다:</p>
<pre><code class="language-python"># Agent Mesh Harness Architecture
class AgentMeshHarness:
    def __init__(self):
        self.execution_harness = ExecutionHarness()      # 실행 환경 관리
        self.memory_harness = MemoryHarness()             # 상태/메모리 관리
        self.permission_harness = PermissionHarness()      # 접근 권한 관리
        self.observability_harness = ObservabilityHarness()  # 모니터링/추적
    
    def verify_agent_contract(self, agent: AgentMeshNode) -> VerificationResult:
        """에이전트가 메쉬에 합류하기 전 필수 검증"""
        checks = [
            self.execution_harness.check_resource_limits(agent),
            self.memory_harness.validate_state_schema(agent),
            self.permission_harness.verify_tool_access_scope(agent),
            self.observability_harness.ensure_traceability(agent)
        ]
        return all(checks)

<h2 id="section-4-agent-mesh-설계-시-핵심-고려사항" tabindex="-1">4. Agent Mesh 설계 시 핵심 고려사항<a href="#section-4-agent-mesh-%EC%84%A4%EA%B3%84-%EC%8B%9C-%ED%95%B5%EC%8B%AC-%EA%B3%A0%EB%A0%A4%EC%82%AC%ED%95%AD" class="heading-anchor" aria-label="4. Agent Mesh 설계 시 핵심 고려사항 항목 링크">#</a></h2>
<h3 id="section-4-1-메쉬-토폴로지-결정" tabindex="-1">4.1 메쉬 토폴로지 결정<a href="#section-4-1-%EB%A9%94%EC%89%AC-%ED%86%A0%ED%8F%B4%EB%A1%9C%EC%A7%80-%EA%B2%B0%EC%A0%95" class="heading-anchor" aria-label="4.1 메쉬 토폴로지 결정 항목 링크">#</a></h3>
<p>에이전트 간 연결 방식은 세 가지 토폴로지로 나뉜다:</p>
<p><strong>Star Mesh</strong>: 오케스트레이터가 중심으로, 모든 에이전트가 오케스트레이터를 통해 간접 통신. 단순하지만 오케스트레이터가 병목이 될 수 있다.</p>
<p><strong>Full Mesh</strong>: 모든 에이전트가 서로 직접 통신. 지연은 낮지만, 에이전트 추가 시 연결 수가 N*(N-1)/2로 증가하여 관리 복잡도가 급증한다.</p>
<p><strong>Hierarchical Mesh</strong>: 계층 구조로 그룹화. 같은 그룹 내 에이전트는 Full Mesh, 그룹 간는 hierarchical 통신. 대규모 시스템에 적합하다.</p>
<h3 id="section-4-2-상태-관리-전략" tabindex="-1">4.2 상태 관리 전략<a href="#section-4-2-%EC%83%81%ED%83%9C-%EA%B4%80%EB%A6%AC-%EC%A0%84%EB%9E%B5" class="heading-anchor" aria-label="4.2 상태 관리 전략 항목 링크">#</a></h3>

<pre><code class="language-python"># 회로 차단기 패턴을 통한 장애 격리

    def __init__(self, agent_id: str, failure_threshold: int = 3):
        self.agent_id = agent_id
        self.failure_count = 0
        self.state = "closed"  # closed → open → half-open
    
    async def execute(self, task: Task, agent: SpecialistAgent):
        if self.state == "open":
            # 즉시 대안 에이전트에게 위임
