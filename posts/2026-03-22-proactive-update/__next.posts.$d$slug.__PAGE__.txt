c:T555c,<h1>Context Engineering의 시대: MCP/A2A 표준화가 왜 2026년의 진짜 백엔드를 다시 쓰는가</h1>
<p>2026년의 에이전트 시장을 보면, 더 이상 핵심 경쟁이 "어느 모델이 더 똑똑한가"에만 머물지 않습니다. 최근 트렌드 리포트들이 공통적으로 가리키는 방향은 더 구체적입니다. <strong>멀티 에이전트 오케스트레이션</strong>, <strong>MCP/A2A 같은 프로토콜 표준화</strong>, <strong>거버넌스 내장형 실행 시스템</strong>, 그리고 <strong>엔지니어의 역할이 구현자에서 오케스트레이터로 이동하는 흐름</strong>이 동시에 가속되고 있습니다.</p>
<p>어제 관점이 브라우저와 로컬 런타임을 "두 번째 백엔드"로 보는 것이었다면, 오늘은 그보다 한 단계 더 안쪽으로 들어가 보겠습니다.</p>
<p>제 결론은 명확합니다.</p>
<blockquote>
<p><strong>2026년의 백엔드는 API를 잘 노출하는 계층이 아니라, 에이전트에게 어떤 맥락(context)을 어떤 계약(contract)으로, 어떤 시점에, 어떤 권한으로 주입할지 설계하는 계층이 된다.</strong></p>
</blockquote>
<p>즉, 이제 중요한 것은 CRUD API의 개수가 아니라 <strong>컨텍스트 엔지니어링(Context Engineering)</strong> 입니다.</p>
<p>이번 글에서는 왜 MCP와 A2A의 표준화가 단순한 연결성 개선이 아니라 백엔드 아키텍처 자체를 바꾸는 사건인지, 그리고 제품 팀이 어떤 경계를 새로 설계해야 하는지 Deep Dive 해보겠습니다.</p>
<h2 id="section-1-rest-이후의-질문-무슨-데이터를-줄까-가-아니라-무슨-맥락을-줄까" tabindex="-1">1. REST 이후의 질문: "무슨 데이터를 줄까"가 아니라 "무슨 맥락을 줄까"<a href="#section-1-rest-%EC%9D%B4%ED%9B%84%EC%9D%98-%EC%A7%88%EB%AC%B8-%EB%AC%B4%EC%8A%A8-%EB%8D%B0%EC%9D%B4%ED%84%B0%EB%A5%BC-%EC%A4%84%EA%B9%8C-%EA%B0%80-%EC%95%84%EB%8B%88%EB%9D%BC-%EB%AC%B4%EC%8A%A8-%EB%A7%A5%EB%9D%BD%EC%9D%84-%EC%A4%84%EA%B9%8C" class="heading-anchor" aria-label="1. REST 이후의 질문: &#x22;무슨 데이터를 줄까&#x22;가 아니라 &#x22;무슨 맥락을 줄까&#x22; 항목 링크">#</a></h2>
<p>기존 백엔드의 질문은 비교적 단순했습니다.</p>
<ul>
<li>어떤 리소스를 저장할 것인가?</li>
<li>어떤 엔드포인트로 노출할 것인가?</li>
<li>어떤 권한으로 읽고 쓸 것인가?</li>
</ul>
<p>하지만 에이전트 시스템에서는 이 질문만으로는 부족합니다. 에이전트는 단순히 데이터를 조회하지 않습니다. <strong>계획하고, 도구를 선택하고, 실행 결과를 해석하고, 다음 액션을 결정</strong>합니다. 즉, 에이전트가 필요로 하는 것은 raw data가 아니라 <strong>의사결정 가능한 형태로 정리된 맥락</strong>입니다.</p>
<p>예를 들어 <code>GET /inventory/42</code> 가 반환하는 값이 아래와 같다고 해봅시다.</p>
<pre><code class="language-json">{ "sku": "42", "stock": 18, "leadTimeDays": 5 }
</code></pre>
<p>인간 개발자에게는 충분할 수 있습니다. 하지만 에이전트가 재발주 여부를 판단해야 한다면 이것만으로는 부족합니다. 필요한 것은 이런 정보입니다.</p>
<ul>
<li>최근 7일 판매 추세</li>
<li>품절 임계치</li>
<li>공급업체 리드타임의 신뢰도</li>
<li>현재 진행 중인 마케팅 캠페인 여부</li>
<li>재발주 승인 권한이 있는지 여부</li>
</ul>
<p>즉, 2026년의 백엔드는 리소스 서버라기보다 <strong>decision substrate</strong> 에 가깝습니다. 데이터를 저장하는 것보다, <strong>모델이 오판하지 않도록 맥락을 조립하는 일</strong>이 더 중요해집니다.</p>
<h2 id="section-2-mcp가-바꾸는-것-툴-연결-표준이-아니라-맥락-공급-표준" tabindex="-1">2. MCP가 바꾸는 것: 툴 연결 표준이 아니라 "맥락 공급 표준"<a href="#section-2-mcp%EA%B0%80-%EB%B0%94%EA%BE%B8%EB%8A%94-%EA%B2%83-%ED%88%B4-%EC%97%B0%EA%B2%B0-%ED%91%9C%EC%A4%80%EC%9D%B4-%EC%95%84%EB%8B%88%EB%9D%BC-%EB%A7%A5%EB%9D%BD-%EA%B3%B5%EA%B8%89-%ED%91%9C%EC%A4%80" class="heading-anchor" aria-label="2. MCP가 바꾸는 것: 툴 연결 표준이 아니라 &#x22;맥락 공급 표준&#x22; 항목 링크">#</a></h2>
<p>MCP(Model Context Protocol)를 단순히 "도구 호출 프로토콜"로 이해하면 절반만 본 겁니다. 실제 제품 관점에서 MCP가 중요한 이유는, 그 프로토콜이 백엔드 팀에게 새로운 책임을 강제하기 때문입니다.</p>
<p>이제 백엔드는 이렇게 질문받습니다.</p>
<ul>
<li>이 도구는 에이전트에게 <strong>무엇을 할 수 있다</strong>고 설명할 것인가?</li>
<li>어떤 입력 스키마가 오해를 최소화하는가?</li>
<li>결과는 숫자만 반환할 것인가, 아니면 <strong>행동에 필요한 해석 단서</strong>까지 반환할 것인가?</li>
<li>실패 시 <code>not_found</code> 와 <code>policy_blocked</code> 를 어떻게 구분해서 알려줄 것인가?</li>
</ul>
<p>결국 MCP 서버는 기존 API gateway의 대체재가 아니라, 더 높은 수준의 <strong>semantic gateway</strong> 입니다.</p>
<p>아래는 단순 조회가 아니라, 에이전트에게 "행동 가능한 맥락"을 반환하는 MCP 툴의 예시입니다.</p>
<pre><code class="language-ts">import { z } from "zod";

type InventorySnapshot = {
  sku: string;
  stock: number;
  leadTimeDays: number;
  soldLast7d: number;
  campaignBoost: boolean;
};

type ContextEnvelope = {
  summary: string;
  riskLevel: "low" | "medium" | "high";
  recommendedAction?: "reorder_now" | "monitor" | "escalate";
  facts: string[];
};

function buildInventoryContext(snapshot: InventorySnapshot): ContextEnvelope {
  const daysLeft = Math.floor(snapshot.stock / Math.max(snapshot.soldLast7d / 7, 1));
  const campaignFactor = snapshot.campaignBoost ? 1.4 : 1.0;
  const projectedDaysLeft = Math.floor(daysLeft / campaignFactor);

  if (projectedDaysLeft &#x3C;= snapshot.leadTimeDays) {
    return {
      summary: "현재 판매 속도 기준으로 리드타임 내 품절 위험이 높습니다.",
      riskLevel: "high",
      recommendedAction: "reorder_now",
      facts: [
        `현재 재고: ${snapshot.stock}`,
        `최근 7일 판매량: ${snapshot.soldLast7d}`,
        `리드타임: ${snapshot.leadTimeDays}일`,
        `프로모션 영향 반영 예상 잔여일: ${projectedDaysLeft}일`
      ]
    };
  }

  return {
    summary: "즉시 재발주까지는 아니지만, 재고 추이를 계속 관찰해야 합니다.",
    riskLevel: "medium",
    recommendedAction: "monitor",
    facts: [
      `현재 재고: ${snapshot.stock}`,
      `예상 잔여일: ${projectedDaysLeft}일`
    ]
  };
}
</code></pre>
<p>이 코드의 핵심은 복잡한 로직이 아닙니다. 핵심은 <strong>백엔드가 더 이상 사실만 전달하지 않고, 에이전트가 안전하게 다음 액션을 고를 수 있도록 의미를 정리해서 넘긴다</strong>는 점입니다.</p>
<p>이 순간부터 백엔드 엔지니어의 산출물은 endpoint가 아니라 <strong>context contract</strong> 가 됩니다.</p>
<h2 id="section-3-a2a가-추가하는-난이도-서비스-통신이-아니라-행위자-간-협상" tabindex="-1">3. A2A가 추가하는 난이도: 서비스 통신이 아니라 "행위자 간 협상"<a href="#section-3-a2a%EA%B0%80-%EC%B6%94%EA%B0%80%ED%95%98%EB%8A%94-%EB%82%9C%EC%9D%B4%EB%8F%84-%EC%84%9C%EB%B9%84%EC%8A%A4-%ED%86%B5%EC%8B%A0%EC%9D%B4-%EC%95%84%EB%8B%88%EB%9D%BC-%ED%96%89%EC%9C%84%EC%9E%90-%EA%B0%84-%ED%98%91%EC%83%81" class="heading-anchor" aria-label="3. A2A가 추가하는 난이도: 서비스 통신이 아니라 &#x22;행위자 간 협상&#x22; 항목 링크">#</a></h2>
<p>MCP가 에이전트와 도구를 연결한다면, A2A(Agent-to-Agent)는 에이전트와 에이전트를 연결합니다. 여기서 백엔드 설계는 한 단계 더 어려워집니다.</p>
<p>왜냐하면 전통적인 서비스 간 통신은 비교적 결정적이기 때문입니다. 주문 서비스가 재고 서비스에 요청을 보내면, 스키마와 상태 코드를 맞추는 문제가 중심이었습니다. 하지만 A2A에서는 다음 문제가 동시에 등장합니다.</p>
<ul>
<li>어떤 에이전트가 어떤 전문성을 가진 것으로 간주되는가?</li>
<li>작업 위임 시 어느 정도의 맥락을 공유해야 하는가?</li>
<li>보조 에이전트가 만든 결과를 누가 검증하는가?</li>
<li>충돌하는 제안이 오면 어느 쪽이 최종 권한을 갖는가?</li>
</ul>
<p>즉, A2A는 단순 RPC가 아니라 <strong>goal-oriented delegation system</strong> 입니다. 서비스 디스커버리보다 더 중요한 것은 <strong>역할, 책임, 검증 루프</strong> 입니다.</p>
<p>여기서 많은 팀이 저지르는 실수는 멀티 에이전트를 "LLM 마이크로서비스"처럼 생각하는 것입니다. 하지만 실제로는 그렇지 않습니다. 멀티 에이전트 시스템은 마이크로서비스보다 훨씬 더 불확실합니다. 각 에이전트는 같은 입력을 받아도 다른 설명을 만들 수 있고, 같은 계획이라도 우선순위를 다르게 둘 수 있습니다.</p>
<p>그래서 A2A 아키텍처는 요청-응답 스키마보다 먼저 아래 세 가지를 고정해야 합니다.</p>
<ol>
<li><strong>권한 경계</strong> — 누가 실행하고 누가 추천만 하는가</li>
<li><strong>검증 경계</strong> — 누가 결과를 승인하고 반려하는가</li>
<li><strong>맥락 경계</strong> — 어떤 기억을 공유하고 어떤 기억은 숨길 것인가</li>
</ol>
<h2 id="section-4-이제-필요한-것은-api-설계가-아니라-context-budget-설계다" tabindex="-1">4. 이제 필요한 것은 API 설계가 아니라 Context Budget 설계다<a href="#section-4-%EC%9D%B4%EC%A0%9C-%ED%95%84%EC%9A%94%ED%95%9C-%EA%B2%83%EC%9D%80-api-%EC%84%A4%EA%B3%84%EA%B0%80-%EC%95%84%EB%8B%88%EB%9D%BC-context-budget-%EC%84%A4%EA%B3%84%EB%8B%A4" class="heading-anchor" aria-label="4. 이제 필요한 것은 API 설계가 아니라 Context Budget 설계다 항목 링크">#</a></h2>
<p>LLM 시스템에서 가장 흔한 실패는 의외로 모델 품질 부족이 아닙니다. 대부분은 <strong>컨텍스트 과잉</strong> 또는 <strong>컨텍스트 누락</strong>입니다.</p>
<ul>
<li>너무 많이 넣으면 토큰 비용이 급증하고, 핵심 신호가 묻힙니다.</li>
<li>너무 적게 넣으면 에이전트가 엉뚱한 가정을 세웁니다.</li>
<li>권한 정보가 빠지면 위험한 액션을 시도합니다.</li>
<li>최신 상태가 빠지면 이미 해결된 문제를 다시 파고듭니다.</li>
</ul>
<p>이 때문에 2026년형 백엔드에는 <code>DB → API → UI</code> 흐름만으로는 부족합니다. 그 위에 <strong>Context Budget Layer</strong> 가 필요합니다.</p>
<p>제가 추천하는 구조는 대략 이렇습니다.</p>
<pre><code class="language-text">[Source Systems]
  ├─ DB / Search / Ticket / Git / Browser State
  ↓
[Context Normalizer]
  ├─ schema alignment
  ├─ freshness tagging
  ├─ conflict detection
  ↓
[Policy &#x26; Budget Layer]
  ├─ capability filtering
  ├─ token budget allocation
  ├─ PII / secret redaction
  ↓
[Planner / Orchestrator]
  ├─ tool choice
  ├─ sub-agent delegation
  └─ retry / recovery strategy
  ↓
[Action Runtime]
</code></pre>
<p>여기서 중요한 것은 <code>Policy &#x26; Budget Layer</code> 입니다. 과거에는 보안과 성능이 별도 concern이었지만, 에이전트 아키텍처에서는 <strong>무엇을 보여줄지</strong>가 곧 보안이자 성능이며 정확도입니다.</p>
<p>즉, Context Engineering은 프롬프트 작성 기교가 아니라 <strong>백엔드의 새 책임 분리</strong>입니다.</p>
<h2 id="section-5-실전-패턴-컨텍스트를-주입-하지-말고-계약된-상태로-조립-하라" tabindex="-1">5. 실전 패턴: 컨텍스트를 "주입"하지 말고 "계약된 상태로 조립"하라<a href="#section-5-%EC%8B%A4%EC%A0%84-%ED%8C%A8%ED%84%B4-%EC%BB%A8%ED%85%8D%EC%8A%A4%ED%8A%B8%EB%A5%BC-%EC%A3%BC%EC%9E%85-%ED%95%98%EC%A7%80-%EB%A7%90%EA%B3%A0-%EA%B3%84%EC%95%BD%EB%90%9C-%EC%83%81%ED%83%9C%EB%A1%9C-%EC%A1%B0%EB%A6%BD-%ED%95%98%EB%9D%BC" class="heading-anchor" aria-label="5. 실전 패턴: 컨텍스트를 &#x22;주입&#x22;하지 말고 &#x22;계약된 상태로 조립&#x22;하라 항목 링크">#</a></h2>
<p>많은 팀이 아직도 에이전트에게 긴 시스템 프롬프트와 다량의 검색 결과를 한 번에 밀어 넣는 방식으로 시스템을 만듭니다. 이건 초기 데모에는 통하지만, 운영 단계에서는 금방 무너집니다.</p>
<p>운영 가능한 구조를 만들려면, 컨텍스트는 문장 뭉치가 아니라 <strong>계약된 상태(contracted state)</strong> 로 조립되어야 합니다.</p>
<p>예를 들면 오케스트레이터는 아래처럼 동작해야 합니다.</p>
<pre><code class="language-ts">type Capability =
  | "repo.read"
  | "repo.write"
  | "git.push"
  | "ticket.read"
  | "ticket.comment"
  | "browser.submit";

type ContextPacket = {
  objective: string;
  facts: string[];
  constraints: string[];
  capabilities: Capability[];
  freshnessTs: string;
  nextBestActions: string[];
};

function assembleContext(params: {
  objective: string;
  facts: string[];
  constraints: string[];
  capabilities: Capability[];
}): ContextPacket {
  return {
    objective: params.objective,
    facts: params.facts.slice(0, 12),
    constraints: params.constraints.slice(0, 8),
    capabilities: params.capabilities,
    freshnessTs: new Date().toISOString(),
    nextBestActions: deriveNextBestActions(params)
  };
}

function deriveNextBestActions(params: {
  objective: string;
  facts: string[];
  constraints: string[];
  capabilities: Capability[];
}) {
  const actions: string[] = [];

  if (params.capabilities.includes("repo.write")) {
    actions.push("필요한 파일 수정 후 변경 요약 생성");
  }
  if (params.capabilities.includes("git.push")) {
    actions.push("최종 승인 조건 확인 후 main 브랜치 반영");
  }
  if (!params.capabilities.includes("browser.submit")) {
    actions.push("외부 제출 액션은 제안만 하고 실제 실행은 보류");
  }

  return actions;
}
</code></pre>
<p>이 패턴의 장점은 분명합니다.</p>
<ul>
<li>에이전트가 자신이 <strong>무엇을 아는지</strong>, <strong>무엇을 할 수 있는지</strong>, <strong>무엇을 하면 안 되는지</strong>를 동시에 이해합니다.</li>
<li>멀티 에이전트 환경에서도 패킷 단위로 맥락을 넘길 수 있습니다.</li>
<li>재시도 시에도 이전 상태를 재조립하기가 쉽습니다.</li>
<li>감사 로그에 남기기 좋습니다.</li>
</ul>
<p>결국 중요한 것은 긴 설명이 아니라 <strong>구조화된 작동 맥락</strong>입니다.</p>
<h2 id="section-6-거버넌스가-아키텍처-내부로-들어온다" tabindex="-1">6. 거버넌스가 아키텍처 내부로 들어온다<a href="#section-6-%EA%B1%B0%EB%B2%84%EB%84%8C%EC%8A%A4%EA%B0%80-%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98-%EB%82%B4%EB%B6%80%EB%A1%9C-%EB%93%A4%EC%96%B4%EC%98%A8%EB%8B%A4" class="heading-anchor" aria-label="6. 거버넌스가 아키텍처 내부로 들어온다 항목 링크">#</a></h2>
<p>2026년 트렌드 리포트들이 공통으로 강조하는 포인트 하나가 있습니다. 에이전트 확산의 병목은 모델 성능보다 <strong>거버넌스와 신뢰성</strong>입니다.</p>
<p>이 말은 꽤 중요합니다. 왜냐하면 많은 팀이 아직도 거버넌스를 "출시 직전 체크리스트" 정도로 취급하기 때문입니다. 하지만 에이전트 시대에는 그 접근이 통하지 않습니다.</p>
<p>거버넌스는 이제 문서가 아니라 <strong>런타임 기능</strong>이어야 합니다.</p>
<p>필수적으로 내장해야 할 것은 최소 이 정도입니다.</p>
<ul>
<li><strong>Capability gating</strong>: 에이전트별 허용 액션 제한</li>
<li><strong>Approval checkpoints</strong>: 외부 상태 변경 전 승인 큐 진입</li>
<li><strong>Traceability</strong>: 어떤 맥락으로 어떤 결정을 내렸는지 로그화</li>
<li><strong>Recovery typing</strong>: 실패를 재시도 가능/인간 개입 필요/정책 차단으로 구분</li>
<li><strong>Context redaction</strong>: 불필요한 민감정보 제거</li>
</ul>
<p>특히 A2A 환경에서는 보조 에이전트에게 너무 많은 맥락을 넘기는 순간, 보안 문제와 비용 문제가 동시에 커집니다. 그래서 앞으로의 백엔드 보안은 요청 인증만으로 끝나지 않습니다. <strong>"이 에이전트가 지금 이 작업을 위해 이 정보까지 볼 필요가 있는가"</strong> 가 핵심 질문이 됩니다.</p>
<p>이건 Zero Trust가 사람과 서비스 사이를 넘어, <strong>에이전트와 컨텍스트 사이로 확장되는 것</strong>에 가깝습니다.</p>
<h2 id="section-7-시니어-엔지니어의-역할은-더-어려워진다-대신-더-중요해진다" tabindex="-1">7. 시니어 엔지니어의 역할은 더 어려워진다. 대신 더 중요해진다<a href="#section-7-%EC%8B%9C%EB%8B%88%EC%96%B4-%EC%97%94%EC%A7%80%EB%8B%88%EC%96%B4%EC%9D%98-%EC%97%AD%ED%95%A0%EC%9D%80-%EB%8D%94-%EC%96%B4%EB%A0%A4%EC%9B%8C%EC%A7%84%EB%8B%A4-%EB%8C%80%EC%8B%A0-%EB%8D%94-%EC%A4%91%EC%9A%94%ED%95%B4%EC%A7%84%EB%8B%A4" class="heading-anchor" aria-label="7. 시니어 엔지니어의 역할은 더 어려워진다. 대신 더 중요해진다 항목 링크">#</a></h2>
<p>CIO와 각종 업계 분석이 공통적으로 말하는 것도 결국 같은 방향입니다. 엔지니어는 점점 더 직접 구현만 하는 사람이 아니라, <strong>AI 에이전트·도구·서비스·정책을 조율하는 시스템 설계자</strong>가 됩니다.</p>
<p>여기서 중요한 오해를 하나 걷어내야 합니다. 이 변화는 엔지니어의 가치가 줄어든다는 뜻이 아닙니다. 오히려 반대입니다.</p>
<p>코드를 직접 500줄 쓰는 일의 상대적 가치가 줄어드는 대신, 아래 능력의 가치가 커집니다.</p>
<ul>
<li>시스템 경계를 잘 자르는 능력</li>
<li>정책과 권한을 설계하는 능력</li>
<li>실패를 분류하고 복구 루프를 설계하는 능력</li>
<li>에이전트에게 줄 맥락을 압축하고 구조화하는 능력</li>
<li>다중 실행 주체의 책임 소재를 명확하게 만드는 능력</li>
</ul>
<p>다르게 말하면, <strong>문법보다 계약이 중요해지고, 함수보다 경계가 중요해지며, 구현보다 오케스트레이션이 중요해집니다.</strong></p>
<p>이건 유행어가 아니라 구조적 변화입니다.</p>
<h2 id="section-결론-2026년의-백엔드는-컨텍스트-제어면-control-plane-이다" tabindex="-1">결론: 2026년의 백엔드는 "컨텍스트 제어면(Control Plane)" 이다<a href="#section-%EA%B2%B0%EB%A1%A0-2026%EB%85%84%EC%9D%98-%EB%B0%B1%EC%97%94%EB%93%9C%EB%8A%94-%EC%BB%A8%ED%85%8D%EC%8A%A4%ED%8A%B8-%EC%A0%9C%EC%96%B4%EB%A9%B4-control-plane-%EC%9D%B4%EB%8B%A4" class="heading-anchor" aria-label="결론: 2026년의 백엔드는 &#x22;컨텍스트 제어면(Control Plane)&#x22; 이다 항목 링크">#</a></h2>
<p>제가 보기에 2026년의 강한 팀은 더 많은 API를 가진 팀이 아닙니다. 더 좋은 프롬프트를 가진 팀도 아닙니다.</p>
<p>강한 팀은 아래를 설계할 수 있는 팀입니다.</p>
<ul>
<li>에이전트에게 어떤 맥락을 언제 줄지</li>
<li>어떤 계약으로 툴과 에이전트를 연결할지</li>
<li>어떤 역할을 어떤 전문 에이전트에게 위임할지</li>
<li>어떤 권한은 자동 실행하고 어떤 권한은 인간 승인으로 넘길지</li>
<li>실패했을 때 어디서부터 복구할지</li>
</ul>
<p>그래서 제 표현으로 정리하면 이렇습니다.</p>
<ul>
<li><strong>MCP는 툴 호출 규격이 아니라 맥락 공급 계약이다.</strong></li>
<li><strong>A2A는 에이전트 채팅이 아니라 책임 분배 프로토콜이다.</strong></li>
<li><strong>백엔드는 데이터 저장소가 아니라 컨텍스트 제어면이 된다.</strong></li>
</ul>
<p>앞으로의 제품 차별화는 모델을 붙였느냐가 아니라, <strong>맥락을 얼마나 정확하고 안전하고 경제적으로 흘려보내느냐</strong>에서 결정됩니다.</p>
<p>그게 바로 지금, Context Engineering을 프롬프트 장인이 아니라 <strong>백엔드 아키텍트의 핵심 역량</strong>으로 봐야 하는 이유입니다.</p>
<h2 id="section-실무-체크리스트" tabindex="-1">실무 체크리스트<a href="#section-%EC%8B%A4%EB%AC%B4-%EC%B2%B4%ED%81%AC%EB%A6%AC%EC%8A%A4%ED%8A%B8" class="heading-anchor" aria-label="실무 체크리스트 항목 링크">#</a></h2>
<p>마지막으로, 지금 팀에 바로 적용해볼 체크리스트를 남깁니다.</p>
