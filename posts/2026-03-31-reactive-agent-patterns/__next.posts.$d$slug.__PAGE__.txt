4:Tfba,<h2 id="section-서론-폴링-아키텍처의-한계" tabindex="-1">서론: 폴링 아키텍처의 한계<a href="#section-%EC%84%9C%EB%A1%A0-%ED%8F%B4%EB%A7%81-%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98%EC%9D%98-%ED%95%9C%EA%B3%84" class="heading-anchor" aria-label="서론: 폴링 아키텍처의 한계 항목 링크">#</a></h2>
<p>현재 많은 에이전트 오케스트레이션 시스템은 폴링(Polling) 루프를 기반으로 합니다. 에이전트는 주기적으로 상태를 조회(Check)하고, 작업을 스케줄링(Schedule)하며, 다시 확인하는 과정을 반복합니다. 이 방식은 단순하지만, 다음과 같은 치명적인 한계를 가집니다.</p>
<ol>
<li><strong>지연 시간 (Latency)</strong>: 이벤트 발생과 에이전트 인식 사이의 간격(Polling Interval)이 존재합니다.</li>
<li><strong>토큰 비효율 (Token Inefficiency)</strong>: 상태 변화가 없는 경우에도 반복적인 조회 호출로 인해 비용과 연산이 낭비됩니다.</li>
<li><strong>확장성 (Scalability)</strong>: 수천 개의 에이전트가 동시에 실행될 때, 폴링 기반은 중앙 관제 시스템에 부하를 집중시킵니다.</li>
</ol>
<h2 id="section-리액티브-옵저버-패턴의-도입" tabindex="-1">리액티브 옵저버 패턴의 도입<a href="#section-%EB%A6%AC%EC%95%A1%ED%8B%B0%EB%B8%8C-%EC%98%B5%EC%A0%80%EB%B2%84-%ED%8C%A8%ED%84%B4%EC%9D%98-%EB%8F%84%EC%9E%85" class="heading-anchor" aria-label="리액티브 옵저버 패턴의 도입 항목 링크">#</a></h2>
<p>이를 극복하기 위한 대안으로, 우리는 **리액티브 옵저버 패턴(Reactive Observer Pattern)**으로 전환해야 합니다. 상태가 변경되었을 때만 에이전트에게 "깨어날 시간"을 알려주는 이벤트 버스(Event Bus)를 활용하는 방식입니다.</p>
<h3 id="section-아키텍처-설계" tabindex="-1">아키텍처 설계<a href="#section-%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98-%EC%84%A4%EA%B3%84" class="heading-anchor" aria-label="아키텍처 설계 항목 링크">#</a></h3>
<ul>
<li><strong>Event Publisher</strong>: 시스템의 상태(파일 변경, API 응답, 사용자 입력)를 게시합니다.</li>
<li><strong>State Store</strong>: 시스템의 현재 상태를 유지하는 중앙 관제소입니다.</li>
<li><strong>Observer Agent</strong>: 특정 조건(Predicate)에 따라 상태 변경 이벤트를 구독하고, 변경이 발생할 때만 실행 루프에 진입합니다.</li>
</ul>
<pre><code class="language-typescript">// 예시: 리액티브 에이전트 관찰자
class AgentObserver {
  subscribe(eventBus: EventBus, predicate: (state: SystemState) => boolean) {
    eventBus.on('stateChange', (state) => {
      if (predicate(state)) {
        this.wakeUpAndExecute(state);
      }
    });
  }
}
</code></pre>
<h2 id="section-실무적-trade-off" tabindex="-1">실무적 Trade-off<a href="#section-%EC%8B%A4%EB%AC%B4%EC%A0%81-trade-off" class="heading-anchor" aria-label="실무적 Trade-off 항목 링크">#</a></h2>
<p>이벤트 기반 구조는 완벽하지 않습니다.</p>
<ol>
<li><strong>복잡성</strong>: 이벤트 루프 디버깅과 상태 일관성 유지가 훨씬 어렵습니다.</li>
<li><strong>보안</strong>: 어떤 이벤트가 어떤 에이전트를 깨울 수 있는지 통제하는 '이벤트 보안 정책'이 필수적입니다.</li>
<li><strong>실패 복구</strong>: 이벤트 전달이 실패했을 때 어떻게 재시도할 것인가에 대한 고민이 필요합니다.</li>
</ol>
<h2 id="section-결론" tabindex="-1">결론<a href="#section-%EA%B2%B0%EB%A1%A0" class="heading-anchor" aria-label="결론 항목 링크">#</a></h2>
